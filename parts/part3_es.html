Almacenamiento y consulta de datos en el CDR

En la parte anterior diseñamos un conjunto de arquetipos y los combinamos en plantillas para representar un flujo de trabajo. En esta parte recorreremos paso a paso las operaciones fundamentales requeridas para persistir (almacenar) y recuperar datos clínicos utilizando un Repositorio de Datos Clínicos (CDR) de openEHR. Nos centraremos en pasos prácticos y directos empleando APIs REST estándar.

Nota: Aunque en los siguientes ejemplos no utilizamos datos clínicos reales (mantenemos la analogía del reparto de pizzas), todo lo expuesto aquí es directamente extrapolable a un flujo de trabajo clínico real.

El Repositorio de Datos Clínicos (CDR)

Como comentamos anteriormente, el CDR es la base de datos que almacena y gestiona los datos de salud. Dado que todas las composiciones almacenadas en un CDR de openEHR están estrictamente gobernadas por plantillas, el CDR debe tener cargadas las plantillas pertinentes antes de poder aceptar cualquier composición basada en ellas.

En esta guía utilizaremos un CDR basado en EHRbase, una implementación de openEHR de código abierto desarrollada por vitagroup AG (vitagroup.ag). Aunque existen diversas implementaciones de CDR en el mercado, EHRbase ofrece un entorno de pruebas (sandbox) público y de libre acceso, ideal para el aprendizaje y la experimentación:

  • URL del entorno de pruebas (sandbox): https://sandkiste.ehrbase.org
  • Documentación completa de la API: Documentación de la API REST openEHR de EHRbase
Nota de seguridad: El entorno de pruebas es un servicio público y compartido. Nunca envíes datos de pacientes reales, contraseñas ni información de identificación personal.

Herramientas para pruebas de API

Para enviar y recuperar datos de los puntos de acceso (endpoints) de EHRbase necesitamos un cliente HTTP/REST. Entre las herramientas más populares figuran Insomnia, Bruno y Postman. En este tutorial utilizaremos Postman, aunque se aplican exactamente las mismas peticiones y conceptos a cualquier otra herramienta de pruebas de API.

Una breve visita guiada por Postman

Al abrir Postman por primera vez, no dejes que su extensa interfaz te abrume. Para nuestro flujo de trabajo con openEHR solo necesitas interactuar con tres zonas principales:

  1. Barra lateral izquierda (Tu biblioteca): Donde residen tus peticiones guardadas. La sección más importante es Collections, donde organizas las peticiones relacionadas en carpetas. Puedes crear colecciones haciendo clic en el botón "+" y seleccionando "Collection". Para crear una petición dentro de tu colección, pasa el cursor sobre la colección y haz clic en el "+" que aparece a su lado.
  2. Panel superior / central (El constructor de peticiones): Donde configuras la llamada HTTP:
    • Método HTTP: El menú desplegable del verbo (GET, POST, PUT, etc.).
    • Barra de URLs: La dirección de destino de tu servidor CDR.
    • Cabeceras (Headers): Metadatos que describen el contenido enviado (p. ej., Content-Type: application/json o Prefer: return=representation).
    • Parámetros (Params): Parámetros de consulta en la URL o variables de ruta (p. ej., :ehr_id o :template_id).
    • Cuerpo (Body): La carga útil de datos (p. ej., la composición en JSON o el contenido XML sin procesar de una plantilla OPT).
    • Autorización (Authorization): Donde se configuran los tokens de portador (bearer tokens) o credenciales básicas al interactuar con sistemas securizados.
  3. Panel inferior (El visor de respuestas): Muestra la respuesta devuelta por el CDR una vez haces clic en Send:
    • Código de estado (Status Code): Confirma el éxito (200 OK, 201 Created) o reporta incidencias (400 Bad Request, 404 Not Found).
    • Cuerpo de respuesta (Response Body): Los datos devueltos (como un nuevo EHR ID generado, el UID de una composición o el resultado de una consulta).
    • Tiempo y tamaño (Time & Size): Métricas de rendimiento de la petición.

Verbos HTTP esenciales en openEHR

Para comunicarle al CDR qué acción deseas realizar con tu petición dispones de distintos «verbos»: GET, POST, PUT, DELETE, PATCH. En todos nuestros ejemplos prácticos utilizaremos exclusivamente GET, POST y PUT. Para consultar la totalidad de capacidades de la API de EHRbase, consulta su documentación oficial.

Método HTTP Significado Uso en openEHR y EHRbase
GET Lectura / Recuperación Obtener datos sin modificar el estado del servidor (p. ej., descargar una plantilla o consultar una composición).
POST Creación / Ejecución Enviar nuevos datos para ser creados (p. ej., registrar una nueva historia EHR, persistir una composición o ejecutar una consulta AQL).
PUT Carga / Sustitución Almacenar o reemplazar un recurso en una URI específica (p. ej., cargar una Plantilla Operativa (OPT) en el endpoint de definiciones, o actualizar una versión existente de una composición).

Cargar una Plantilla Operativa (OPT) en el CDR

Antes de poder almacenar una composición, su plantilla correspondiente debe cargarse como archivo de Plantilla Operativa (.opt). El CDR analiza esta definición y aplica todas las restricciones modeladas sobre las composiciones que reciba.

Puedes encontrar los archivos de plantilla de ejemplo en el paquete descargable: Descargar archivos de ejemplo (.zip)

MétodoPOST
URLhttps://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/definition/template/adl1.4
Cabeceras (Headers)Prefer: return=representation
Content-Type: application/xml
Cuerpo (Body)Contenido XML sin procesar del archivo .opt.
Estado esperado201 Created
Cuerpo de respuestaLa plantilla OPT registrada en formato XML.
Importante: Si en el servidor ya existe una plantilla con exactamente el mismo template_id, el CDR rechazará la subida para preservar la integridad de versiones.

Generar una composición de ejemplo

Al desarrollar aplicaciones para openEHR, resulta muy útil poder generar con rapidez una composición de ejemplo para una plantilla. Puedes solicitar al CDR que genere una estructura JSON de muestra basada en una plantilla registrada:

MétodoGET
URLhttps://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/definition/template/adl1.4/:template_id/example?format=JSON
Parámetros (Params)template_id = Customer_Review_v0 (según el identificador de la plantilla)
Estado esperado200 OK
Cuerpo de respuestaComposición sintética de ejemplo en formato Canonical JSON de openEHR.
Aviso: Los datos de ejemplo generados por el CDR están destinados estrictamente a la inspección sintáctica. Rellenan los campos con valores arbitrarios y aleatorios, y nunca deben enviarse directamente como registros clínicos.

Crear una Historia Clínica Electrónica (EHR)

En openEHR, las composiciones clínicas no pueden existir de forma aislada. Deben pertenecer a un EHR que represente al paciente (o al cliente, en nuestra analogía de la pizza). Crear un EHR genera un identificador único y persistente (un UUID llamado ehr_id):

MétodoPOST
URLhttps://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/ehr
Cabeceras (Headers)Prefer: return=representation
Estado esperado201 Created
Cuerpo de respuestaMetadatos del registro EHR creado, incluyendo el ehr_id.
Si lo deseas, puedes practicar todo esto subiendo nuestras plantillas de ejemplo al sandbox del CDR.

Construir una composición desde cero (paso a paso)

Una vez que tenemos nuestras plantillas cargadas en el CDR, podemos persistir datos clínicos reales. En openEHR, los datos clínicos se almacenan en forma de una COMPOSITION.

Aunque podrías solicitar a EHRbase una muestra sintética, esas cargas autogeneradas están repletas de valores ficticios y atributos opcionales que dificultan ver qué es realmente necesario. La mejor manera de comprender a fondo los datos de openEHR es construir una composición mínima y válida desde cero.

En este recorrido práctico, construiremos una composición completa para nuestra plantilla Customer_Review_v0.

Por favor, consulta las especificaciones de la clase COMPOSITION. Es una excelente idea seguir la creación del archivo de composición apoyándote en el Modelo de Referencia. Para búsquedas rápidas, recomendamos la herramienta no oficial openEHR RM Browser.

Paso 1 - La anatomía de una COMPOSITION

La COMPOSITION es el contenedor de todo el documento que deseamos persistir. En el nivel raíz, el Modelo de Referencia de openEHR espera esta estructura esquemática: 

{
  "_type": "COMPOSITION",
  "name": { ... },
  "archetype_node_id": "openEHR-EHR-COMPOSITION.example_base.v0",
  "archetype_details": { ... },
  "language": { ... },
  "territory": { ... },
  "category": { ... },
  "composer": { ... },
  "content": [ ... ]
}
Nota: Esta estructura está simplificada. Hemos reducido los elementos al mínimo para facilitar el trabajo con los ejemplos. Consulta la especificación de openEHR para ver la lista completa de atributos de una composición.

Ahora examinaremos y construiremos cada uno de estos atributos individualmente.

Paso 2 - El atributo name (Clase RM: DV_TEXT)

En openEHR, incluso las etiquetas simples rara vez son cadenas de texto plano. Se encapsulan en un tipo de datos del Modelo de Referencia, habitualmente DV_TEXT (Data Value: Text), lo que permite gestionar la localización y los juegos de caracteres.

Para la composición raíz, suele coincidir con el nombre de la plantilla:

"name": {
  "_type": "DV_TEXT",
  "value": "Customer_Review_v0"
}
Nota: Según cómo se haya diseñado tu plantilla, el nombre visible puede diferir del identificador del arquetipo subyacente.

Paso 3 - El atributo archetype_details (Clase RM: ARCHETYPED)

¿Cómo sabe el CDR qué reglas y restricciones debe validar para esta composición? A través de archetype_details. Este objeto vincula la composición tanto con su arquetipo raíz como con la plantilla operativa específica:

Figura 3.8: Árbol de atributos de archetype_details en el openEHR RM Browser.

Observa que archetype_id y template_id tampoco son texto plano; son instancias de las clases ARCHETYPE_ID y TEMPLATE_ID: 

"archetype_details": {
  "_type": "ARCHETYPED",
  "archetype_id": {
    "_type": "ARCHETYPE_ID",
    "value": "openEHR-EHR-COMPOSITION.example_base.v0"
  },
  "template_id": {
    "_type": "TEMPLATE_ID",
    "value": "Customer_Review_v0"
  },
  "rm_version": "1.1.0"
}

Paso 4 - Idioma y territorio (Clase RM: CODE_PHRASE)

Los datos sanitarios tienen un alcance multinacional. Toda composición define explícitamente su idioma principal y su jurisdicción territorial mediante CODE_PHRASE, que asocia un identificador de terminología estándar con un código concreto.

Los códigos admitidos pueden consultarse en las especificaciones de openEHR Support Terminology.

Idioma: ISO 639-1

    "value": "ISO_639-1"

  "code_string": "en"

Territorio: ISO 3166-1

Paso 5 - El atributo category (Clase RM: DV_CODED_TEXT)

openEHR categoriza los contactos clínicos en grandes patrones (como event, persistent o episodic). Utilizamos DV_CODED_TEXT, que vincula texto legible para humanos con un código de terminología interna de openEHR (aquí, el código 433 representa un «evento» o contacto puntual en el tiempo):

Los códigos admitidos se encuentran en la especificación de openEHR Support Terminology.

Figura 3.11: Árbol de atributos de category.

  "_type": "DV_CODED_TEXT",
  "value": "event",
  "defining_code": {
    "_type": "CODE_PHRASE",
    "terminology_id": {
      "_type": "TERMINOLOGY_ID",

Paso 6 - El atributo composer

Todo registro clínico debe registrar su autoría. En openEHR, el autor (composer) se modela como un PARTY_PROXY. Generalmente se elige entre:

  • PARTY_SELF: Se utiliza cuando es el propio paciente quien registra los datos (p. ej., resultados informados por el paciente / PROMs, aplicaciones móviles).
  • PARTY_IDENTIFIED: Se utiliza cuando se recoge el nombre de un profesional externo o el identificador de un proveedor de salud.

Figura 3.12: Elección de PARTY_IDENTIFIED para representar al composer.

"composer": {
  "_type": "PARTY_IDENTIFIED",
  "name": "Max Mustermann"
}

Paso 7 - La sección content: añadir entradas clínicas

Llegamos ahora a la carga de datos propiamente dicha: la matriz content. En nuestra plantilla, incluimos un arquetipo de tipo EVALUATION (openEHR-EHR-EVALUATION.customer_review.v0).

Figura 3.13: Inspección de los atributos obligatorios de un ENTRY dentro de content.

Dado que teóricamente cualquier arquetipo de entrada puede extraerse, citarse o traducirse de forma independiente, openEHR exige que cada entrada defina su propio contexto local:

  • encoding: Codificación de caracteres (p. ej., UTF-8).
  • language: Código de idioma para esta entrada específica.
  • subject: Sobre quién recae esta evaluación clínica. En nuestro caso, PARTY_SELF indica que se aplica directamente al titular de este registro.
  • protocol: Metadatos contextuales sobre cómo o por qué se registró la información (p. ej., el Order ID).
  • data: Las observaciones o evaluaciones clínicas centrales.

La sección content contiene una lista de todos los arquetipos modelados en esta parte de la plantilla. Podemos añadir, al igual que hicimos antes, el encoding, language y subject del contenido:

AQL: consultar datos clínicos específicos

En los pasos anteriores persistimos datos en el CDR y vimos cómo recuperar una composición completa mediante la API cuando conocemos su identificador único. Sin embargo, en aplicaciones clínicas reales rara vez conocerás el ID de la composición de antemano, o solo requerirás puntos de datos específicos (p. ej., únicamente el nombre de la pizza, o la lectura de la presión arterial sistólica) a lo largo de múltiples contactos asistenciales. Para esto, openEHR proporciona el Archetype Query Language (AQL).

AQL está estandarizado en las especificaciones oficiales de openEHR: Especificaciones AQL de openEHR.

En esta sección recorreremos ejemplos prácticos que te proporcionarán un primer contacto intuitivo y directo con AQL.

Ejecutar una consulta AQL mediante la API REST

Las consultas AQL se envían a EHRbase mediante una petición HTTP POST al endpoint de consultas:

Método POST
URL https://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/query/aql
Cabeceras (Headers) Content-Type: application/json
Cuerpo (Body) Carga útil: el envoltorio de la consulta AQL en formato JSON.
Estado esperado 200 OK
Cuerpo de respuesta Columnas y filas del resultado de la consulta en formato JSON.

El cuerpo JSON enviado en la petición sigue esta estructura:

{
  "q": "SELECT ...",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {}
}
  • q: La cadena de la consulta AQL (obligatoria).
  • offset: Número de filas iniciales que se omiten (muy útil para paginación).
  • fetch: Número máximo de filas a devolver (también puede especificarse dentro de la consulta mediante LIMIT).
  • query_parameters: Un diccionario de parámetros clave-valor que se sustituyen en las variables declaradas en la consulta (con el prefijo $).

Las consultas AQL estándar en JSON deben formatearse en una única línea. Para inspeccionar, formatear y documentar consultas de múltiples líneas con comodidad, puedes utilizar la herramienta de código abierto openEHR AQL Manager.

La anatomía de una consulta AQL

A grandes rasgos, una consulta AQL le pregunta al CDR: «Por favor, devuélveme un conjunto de elementos de datos clínicos basándote en rutas de arquetipos y criterios específicos.»

Por ejemplo, comparemos una pregunta en lenguaje natural con su sentencia AQL equivalente (aplicada a nuestra analogía de pedidos de pizza):

Objetivo: ¿Qué clientes han realizado un pedido?
Pregunta en lenguaje natural Cláusula AQL
«Dime todos los EHR IDs...» SELECT e/ehr_id/value
«...de los registros que contengan composiciones...» FROM EHR e CONTAINS COMPOSITION c
«...basadas en la plantilla 'Online_Customer_Order_v0'.» WHERE c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

Uniendo todas las piezas en una consulta completa:

SELECT e/ehr_id/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

AQL 1 - Listar todos los pedidos de un cliente

Nuestro objetivo es encontrar todos los pedidos realizados por nuestro cliente, devolviendo el UUID único de cada composición basada en Online_Customer_Order_v0.

Comenzamos con la estructura básica de contención:

SELECT ... FROM EHR e CONTAINS COMPOSITION c ...

En el Modelo de Referencia de openEHR, el identificador versionado de la composición se ubica en el atributo uid. Si seleccionamos directamente c/uid, el CDR devuelve el objeto OBJECT_VERSION_ID completo: 

{
  "_type": "OBJECT_VERSION_ID",
  "value": "3b463d4c-1613-410f-b271-3e81a7743549::local.ehrbase.org::1"
}

Si nuestra aplicación cliente solo necesita la cadena de texto en sí, podemos apuntar directamente a c/uid/value.

¿Conviene seleccionar el objeto completo o solo el valor? Seleccionar el objeto completo preserva los metadatos (como los tipos de datos y los identificadores de terminología). Por otro lado, apuntar directamente a /value genera una respuesta más limpia y minimiza el procesamiento en el lado del cliente. En estos ejemplos seleccionaremos directamente los valores primitivos.

A continuación, restringimos la consulta al registro de nuestro cliente específico usando su EHR ID (que se encuentra en ehr_id/value del EHR):

SELECT c/uid/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43'

Finalmente, para evitar coincidir con otras composiciones (como reseñas o registros de seguimiento), filtramos específicamente por el ID de la plantilla (situado en archetype_details/template_id/value de la composición): 

SELECT c/uid/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE 
    e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43' 
    AND 
    c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

Al ejecutar esta consulta en Postman obtenemos nuestros tres pedidos registrados:

AQL 2 - Consultar el estado de preparación de los pedidos

En este ejemplo queremos consultar el estado de preparación de nuestros pedidos. Esta información está almacenada en las composiciones basadas en la plantilla Kitchen_And_Delivery_Tracker_v0.

Para determinar las rutas AQL exactas de estos elementos, consultamos el openEHR Archetype Designer. En los detalles del nodo encontramos la ruta resuelta para el Order ID: 

/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]

Figura 3.18: Inspección de la ruta resuelta para el Order ID en el Archetype Designer.

De forma análoga, localizamos la ruta para el estado de transición ISM de la acción (el estado de preparación): 

/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition

Figura 3.19: Localización de la ruta para el estado de transición ISM.

Construimos la sentencia AQL completa:

SELECT 
  c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]/value/id, 
  c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition/current_state/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE 
    e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43' 
    AND 
    c/archetype_details/template_id/value = 'Kitchen_And_Delivery_Tracker_v0'

Escribir valores literales directamente en cadenas AQL largas suele ser propenso a errores. Al reemplazar los valores literales por parámetros (como $ehr_id y $template_id), logramos que nuestra consulta sea limpia, dinámica y reutilizable: 

{
  "q": "SELECT c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]/value/id, c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition/current_state/value FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value=$ehr_id AND c/archetype_details/template_id/value=$template_id",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {
    "ehr_id": "7fab0168-e79f-456f-b271-02050dabaa43",
    "template_id": "Kitchen_And_Delivery_Tracker_v0"
  }
}

Al ejecutar esta petición obtenemos el Order ID y el estado actual de preparación:

Figura 3.20: Identificadores de pedido recuperados con su estado actual de preparación.

AQL 3 - Evaluar puntuaciones por nombre de pizza

Finalmente, determinaremos qué pizza obtuvo la mayor puntuación de satisfacción por parte del cliente.

Aquí encontramos un reto clásico de modelado en openEHR: el nombre de la pizza se registró en el momento del pedido en Online_Customer_Order_v0, mientras que la valoración de satisfacción se envió posteriormente en Customer_Review_v0. Aunque ciertas técnicas avanzadas de AQL permiten vincular registros relacionados, en entornos de producción suele ser más limpio y eficiente ejecutar dos consultas específicas y cruzarlas mediante su identificador común (el Order ID):

  1. Consulta 1: Recuperar el nombre de la pizza para cada Order ID.
  2. Consulta 2: Recuperar la valoración del cliente para cada Order ID.

Consulta 1: Obtener nombres de pizza por Order ID

{
  "q": "SELECT c/uid/value AS order_id, c/content[openEHR-EHR-INSTRUCTION.pizza_order.v0]/activities[at0001]/description[at0002]/items[at0004]/value/value AS pizza_name FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value=$ehr_id AND c/archetype_details/template_id/value=$template_id",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {
    "ehr_id": "7fab0168-e79f-456f-b271-02050dabaa43",
    "template_id": "Online_Customer_Order_v0"
  }
}

Figura 3.22: Salida que asocia identificadores de pedido con nombres específicos de pizza.

Consulta 2: Obtener valoraciones por Order ID

{
  "q": "SELECT c/content[openEHR-EHR-EVALUATION.customer_review.v0]/protocol[at0001]/items[at0002]/value/id AS order_id, c/content[openEHR-EHR-EVALUATION.customer_review.v0]/data[at0003]/items[at0005]/value/magnitude AS rating FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value=$ehr_id AND c/archetype_details/template_id/value=$template_id",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {
    "ehr_id": "7fab0168-e79f-456f-b271-02050dabaa43",
    "template_id": "Customer_Review_v0"
  }
}

Figura 3.23: Salida que vincula identificadores de pedido con puntuaciones numéricas de satisfacción.
