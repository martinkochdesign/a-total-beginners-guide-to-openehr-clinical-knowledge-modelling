Capítulo 7: Primeros pasos con el CDR y las APIs REST

Diseñar modelos clínicos en nuestro puesto de trabajo es solo el inicio; la verdadera prueba llega cuando esos modelos interactúan con un servidor en producción. En este capítulo presentamos el Repositorio de Datos Clínicos (CDR / RDC) como el motor central de persistencia de openEHR y nos conectamos al entorno de pruebas público de EHRbase. Exploramos la estructura esencial de Postman, repasamos los métodos HTTP estándar y ejecutamos nuestra primera comprobación de estado para verificar que el servidor está operativo.

En la parte anterior diseñamos un conjunto de arquetipos y los ensamblamos en plantillas para representar un flujo de trabajo asistencial. En esta parte recorreremos las operaciones nucleares necesarias para persistir (almacenar) y recuperar datos clínicos utilizando un Repositorio de Datos Clínicos (CDR / RDC) de openEHR. Nos centraremos en pasos prácticos y aplicados empleando APIs REST estándar.

Nota: Aunque en los siguientes ejemplos no empleamos datos clínicos reales (mantenemos la analogía del reparto de pizzas), todo lo expuesto aquí es directamente transferible a un circuito asistencial.

7.1 El Repositorio de Datos Clínicos (CDR / RDC)

Como comentamos anteriormente, el CDR es la base de datos que almacena y gestiona la información sanitaria. Debido a que todas las composiciones almacenadas en un CDR de openEHR están rigurosamente gobernadas por plantillas, el repositorio debe almacenar las plantillas correspondientes antes de poder admitir cualquier composición basada en ellas.

En esta guía utilizaremos un CDR sustentado en EHRbase, una implementación de código abierto de openEHR desarrollada por vitagroup AG (vitagroup.ag). Aunque existen diversas implementaciones de CDR en el mercado, EHRbase ofrece un entorno de pruebas (sandbox) público y de libre acceso, idóneo para el aprendizaje y la experimentación:

  • URL del entorno de pruebas: https://sandkiste.ehrbase.org
  • Documentación completa de la API: Documentación de la API REST openEHR de EHRbase
Aviso de seguridad: El entorno de pruebas es un servicio público y compartido. Nunca envíes datos reales de pacientes, contraseñas ni información personal identificativa.

7.2 Herramientas para pruebas de API

Para enviar datos y recuperarlos de los puntos de acceso (endpoints) de EHRbase necesitamos un cliente HTTP/REST. Entre las herramientas más populares se encuentran Insomnia, Bruno o Postman. En este tutorial emplearemos Postman, si bien las mismas peticiones y conceptos aplican de forma idéntica a cualquier otra herramienta de pruebas de API.

Un breve recorrido por Postman

Al abrir Postman por primera vez, no dejes que la densidad de su interfaz te intimide. Para nuestro flujo de trabajo en openEHR solo necesitas interactuar con tres áreas principales:

  1. Barra lateral izquierda (Tu biblioteca): Donde residen tus peticiones guardadas. La sección primordial es Collections (colecciones), donde organizas peticiones relacionadas en carpetas. Puedes crear colecciones pulsando en el «+» y seleccionando «Collection». Para crear una petición dentro de tu colección, pasa el cursor sobre ella y pulsa en el «+» que aparece a su lado.
  2. Panel superior / central (El constructor de peticiones): Donde configuras la llamada HTTP:
    • Método HTTP: El desplegable de verbos (GET, POST, PUT, etc.).
    • Barra de URL: La dirección de destino de tu servidor CDR.
    • Cabeceras (Headers): Metadatos que describen la carga útil (p. ej., Content-Type: application/json o Prefer: return=representation).
    • Parámetros (Params): Parámetros de consulta URL o variables de ruta (p. ej., :ehr_id o :template_id).
    • Cuerpo (Body): La carga de datos enviada (p. ej., la composición en JSON o el XML en bruto de una plantilla OPT).
    • Autorización (Authorization): Donde se configuran tokens portadores o credenciales al interactuar con entornos protegidos.
  3. Panel inferior (El visor de respuestas): Muestra la respuesta devuelta por el CDR una vez pulsas en Send:
    • Código de estado (Status Code): Confirma el éxito (200 OK, 201 Created) o alerta de incidencias (400 Bad Request, 404 Not Found).
    • Cuerpo de respuesta (Response Body): Los datos devueltos (como un nuevo EHR ID generado, un UID de composición o el resultado de una consulta).
    • Tiempo y tamaño (Time & Size): Métricas de rendimiento relativas a la duración y el volumen de la respuesta.

Figura 7.1: Interfaz gráfica de usuario de Postman.

Verbos HTTP principales

Para indicarle al CDR qué acción deseas ejecutar en tu petición dispones de distintos «verbos»: GET, POST, PUT, DELETE, PATCH. En todos nuestros ejemplos prácticos emplearemos de forma exclusiva GET, POST y PUT. Para consultar la totalidad de funciones de la API, consulta la documentación oficial de EHRbase.

Método HTTP Significado Uso en openEHR y EHRbase
GET Leer / Recuperar Recuperar información sin alterar el estado del servidor (p. ej., descargar una plantilla o consultar una composición).
POST Crear / Ejecutar Enviar datos nuevos para su creación (p. ej., dar de alta un registro EHR, persistir una nueva composición o ejecutar una consulta AQL).
PUT Subir / Reemplazar Almacenar o actualizar un recurso en una URI concreta (p. ej., subir una plantilla operativa (OPT) al endpoint de definición de plantillas, o actualizar una versión existente de una composición).

Comprobación del estado del servidor

Como verificación básica para garantizar que el CDR está operativo y accesible, llamamos al endpoint de estado del servidor. Una respuesta 200 OK confirmará que el servicio está activo.

Dado que es la primera vez que empleamos la herramienta para emitir una petición, sigamos el proceso paso a paso:

  1. Crea una colección en la barra lateral izquierda (si no lo has hecho ya).
  2. Añade una nueva petición a tu colección.
  3. En el constructor principal, selecciona GET en el desplegable de métodos situado a la izquierda de la barra de URL.
  4. En la barra de URL, introduce https://sandkiste.ehrbase.org/ehrbase/rest/status.
  5. Navega por las pestañas situadas bajo la barra de URL («Params», «Headers» y «Body»). No hace falta añadir nada aquí por ahora, pero echa un vistazo. Observa que «Headers» utiliza pares clave-valor, los cuales necesitaremos en ejemplos posteriores.
  6. Haz clic en el botón Send situado a la derecha de la barra de URL.
  7. Tras un breve instante, la respuesta aparecerá en el panel inferior.

Capítulo 9: Persistencia de datos clínicos: el EHR y las composiciones

Con las plantillas activas en el servidor, nos adentramos en el núcleo de la persistencia en openEHR: la creación de las historias clínicas (EHR) de los pacientes y su carga con datos estructurados. En este capítulo creamos un nuevo contenedor EHR, construimos paso a paso desde cero una composición canónica en JSON totalmente válida, la registramos en el CDR y demostramos cómo aplicar modificaciones seguras mediante bloqueo optimista e identificadores de versión.

9.1 Generar una composición de ejemplo

Al desarrollar aplicaciones sobre openEHR, resulta sumamente útil poder generar con rapidez una composición de ejemplo a partir de una plantilla. Puedes solicitar al CDR que cree una estructura JSON de muestra basada en una plantilla registrada:

MétodoGET
URLhttps://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/definition/template/adl1.4/:template_id/example?format=JSON
Parámetros (Params)template_id = Customer_Review_v0 (según el identificador de la plantilla)
Estado esperado200 OK
Cuerpo de la respuestaComposición sintética de ejemplo en formato JSON Canónico de openEHR.
Advertencia: Las composiciones de ejemplo generadas por el CDR están pensadas estrictamente para verificar la sintaxis. Rellenan los campos con valores arbitrarios al azar y nunca deben registrarse como datos clínicos reales.

9.2 Crear un Electronic Health Record (EHR)

En openEHR, las composiciones clínicas no pueden existir de manera aislada. Deben pertenecer obligatoriamente a un EHR que represente al paciente (o cliente, en nuestra analogía de la pizza). La creación de un EHR genera un identificador persistente y único (un UUID de ehr_id):

MétodoPOST
URLhttps://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/ehr
Cabeceras (Headers)Prefer: return=representation
Estado esperado201 Created
Cuerpo de la respuestaMetadatos del registro EHR creado, incluyendo el ehr_id.

9.3 Construir una composición desde cero (paso a paso)

Una vez que nuestras plantillas están cargadas en el CDR, podemos persistir datos clínicos reales. En openEHR, la información clínica se almacena en forma de una COMPOSITION.

Aunque podrías solicitar una muestra sintética a EHRbase, esas estructuras automáticas están repletas de valores ficticios y atributos opcionales que confunden y ocultan lo estrictamente necesario. La mejor forma de comprender las estructuras de datos de openEHR es construir una composición mínima y válida desde cero.

En esta guía paso a paso construiremos una composición completa para nuestra plantilla Customer_Review_v0.

Por favor, consulta las especificaciones formales de la clase COMPOSITION. Es muy recomendable seguir la construcción del archivo utilizando el Modelo de Referencia. Para búsquedas rápidas, recomendamos el navegador no oficial openEHR RM Browser.

Paso 1 — La anatomía de una COMPOSITION

La COMPOSITION es el contenedor de todo el documento que deseamos persistir. En el nivel raíz, el Modelo de Referencia de openEHR espera este esqueleto estructural: 

{
  "_type": "COMPOSITION",
  "name": { ... },
  "archetype_node_id": "openEHR-EHR-COMPOSITION.example_base.v0",
  "archetype_details": { ... },
  "language": { ... },
  "territory": { ... },
  "category": { ... },
  "composer": { ... },
  "content": [ ... ]
}
Nota: Esta estructura se ha simplificado. Hemos reducido los elementos para que los ejemplos resulten claros. Consulta la especificación de openEHR para ver la lista completa de atributos de una composición.

A continuación, examinaremos y construiremos cada uno de estos atributos individualmente.

Paso 2 — El atributo name (Clase RM: DV_TEXT)

En openEHR, incluso las etiquetas más simples rara vez son cadenas de texto ordinarias. Se encapsulan dentro de un tipo de datos del Modelo de Referencia, normalmente DV_TEXT (Data Value: Text), lo que permite gestionar la localización y los juegos de caracteres.

Para la composición raíz, suele coincidir con el nombre de la plantilla:

"name": {
  "_type": "DV_TEXT",
  "value": "Customer_Review_v0"
}
Nota: Según cómo se haya configurado la plantilla, el nombre visible puede diferir del identificador técnico del arquetipo.

Paso 3 — El atributo archetype_details (Clase RM: ARCHETYPED)

¿Cómo sabe el CDR contra qué reglas y restricciones debe validar esta composición? A través de archetype_details. Este objeto vincula la composición tanto con su arquetipo base raíz como con la plantilla operativa específica:

Figura 9.3: Consulta del árbol de atributos de archetype_details en openEHR RM Browser.

Observa que archetype_id y template_id tampoco son texto plano; son instancias de las clases ARCHETYPE_ID y TEMPLATE_ID: 

"archetype_details": {
  "_type": "ARCHETYPED",
  "archetype_id": {
    "_type": "ARCHETYPE_ID",
    "value": "openEHR-EHR-COMPOSITION.example_base.v0"
  },
  "template_id": {
    "_type": "TEMPLATE_ID",
    "value": "Customer_Review_v0"
  },
  "rm_version": "1.1.0"
}

Paso 4 — Idioma y territorio (Clase RM: CODE_PHRASE)

La información sanitaria tiene un alcance multinacional. Cada composición define explícitamente su idioma principal y su ámbito territorial mediante CODE_PHRASE, que asocia un identificador de terminología estándar con un código específico.

Los códigos admitidos pueden consultarse en las especificaciones de openEHR Support Terminology.

Paso 5 — El atributo category (Clase RM: DV_CODED_TEXT)

openEHR categoriza los encuentros asistenciales en patrones generales (tales como event, persistent o episodic). Empleamos DV_CODED_TEXT, que enlaza un texto comprensible con un código de terminología interna de openEHR (aquí, el código 433 representa un evento asistencial puntual o «event»):

Los códigos soportados se detallan en la especificación de openEHR Support Terminology.

Paso 6 — El atributo composer

Todo registro asistencial debe documentar su autoría. En openEHR, el autor (composer) se modela como un PARTY_PROXY. Normalmente se escoge entre:

  • PARTY_SELF: Utilizado cuando el propio paciente ha registrado los datos (p. ej., cuestionarios de resultados reportados por el paciente / PROMs, aplicaciones móviles).
  • PARTY_IDENTIFIED: Utilizado cuando se documenta el nombre de una persona externa o un identificador de un profesional o centro sanitario.

Figura 9.7: Elección de PARTY_IDENTIFIED para representar al autor.

"composer": {
  "_type": "PARTY_IDENTIFIED",
  "name": "Max Mustermann"
}

Paso 7 — La sección content: incorporación de entradas clínicas

Llegamos ahora a la carga asistencial propiamente dicha: el array content. En nuestra plantilla habíamos ubicado un arquetipo de tipo EVALUATION (openEHR-EHR-EVALUATION.customer_review.v0).

Figura 9.8: Inspección de los atributos obligatorios de ENTRY dentro de content.

Dado que cualquier arquetipo de entrada puede, teóricamente, extraerse, citarse o traducirse de forma autónoma, openEHR exige que cada entrada defina su propio contexto localizado:

  • encoding: La codificación de caracteres (p. ej., UTF-8).
  • language: El código de idioma para esta entrada específica.
  • subject: A quién hace referencia esta evaluación. En nuestro caso, PARTY_SELF indica que aplica directamente al titular de la historia clínica.
  • protocol: Metadatos contextuales sobre cómo o por qué se documentó la entrada (p. ej., el Order ID).
  • data: Las observaciones o evaluaciones clínicas nucleares.

Capítulo 10: Consulta de datos clínicos específicos con AQL

Almacenar la información asistencial es solo una parte del recorrido; recuperar valores específicos a través de múltiples visitas y contactos es donde openEHR despliega su mayor potencial. En este capítulo introducimos el Archetype Query Language (AQL): el estándar de consulta agnóstico de proveedores diseñado expresamente para estructuras clínicas. Desglosamos la anatomía de las sentencias AQL, las ejecutamos a través de la API REST y presentamos patrones reales de uso como la parametrización, la inspección de rutas y el cruce de registros entre distintas composiciones.

10.1 Consulta de datos clínicos específicos mediante AQL

En los pasos anteriores almacenamos datos en el CDR y vimos cómo recuperar una composición completa vía API conociendo su identificador unívoco. No obstante, en aplicaciones asistenciales reales rara vez sabrás el ID de la composición de antemano, o solo requerirás puntos de datos concretos (p. ej., solo el nombre de la pizza o solo la toma sistólica de presión arterial) repartidos entre multitud de visitas. Para este cometido, openEHR proporciona el Archetype Query Language (AQL).

AQL está formalizado en las especificaciones oficiales de openEHR: Especificaciones de AQL en openEHR.

En esta sección recorreremos ejemplos prácticos para brindarte un primer contacto intuitivo y práctico con AQL.

Ejecutar una consulta AQL a través de la API REST

Las consultas AQL se remiten a EHRbase utilizando una petición HTTP POST al endpoint de consultas:

Método POST
URL https://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/query/aql
Cabeceras (Headers) Content-Type: application/json
Cuerpo (Body) Payload: la envolvente de la consulta AQL en formato JSON.
Estado esperado 200 OK
Cuerpo de la respuesta Columnas y filas con los resultados de la consulta en formato JSON.

La carga útil en JSON enviada en el cuerpo de la petición sigue esta estructura:

{
  "q": "SELECT ...",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {}
}
  • q: La cadena de texto con la consulta AQL (obligatoria).
  • offset: El número de filas iniciales a omitir (muy útil para paginación).
  • fetch: El número máximo de filas a devolver (también puede establecerse en la propia consulta con LIMIT).
  • query_parameters: Un diccionario de parámetros clave-valor que se sustituyen en las variables declaradas en la consulta (con el prefijo $).

Las consultas AQL estándar en JSON deben formatearse en una única línea. Para inspeccionar, formatear y documentar consultas multilínea cómodamente, puedes utilizar la herramienta de código abierto openEHR AQL Manager.

La anatomía de una consulta AQL

A grandes rasgos, una consulta AQL le pide al CDR: «Por favor, devuélveme un conjunto de elementos de datos clínicos a partir de unas rutas de arquetipo y unos criterios específicos.»

Por ejemplo, comparemos una pregunta formulada en lenguaje natural con su sentencia AQL equivalente (aplicada a nuestra analogía del reparto de pizzas):

Propósito: ¿Qué clientes han realizado un pedido?
Pregunta en lenguaje coloquial Cláusula AQL
«Indícame todos los identificadores de EHR...» SELECT e/ehr_id/value
«...de las historias que contengan composiciones...» FROM EHR e CONTAINS COMPOSITION c
«...basadas en la plantilla 'Online_Customer_Order_v0'.» WHERE c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

Integrando todas las partes en una consulta completa:

SELECT e/ehr_id/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

AQL 1 — Listar todos los pedidos de un cliente

Nuestro propósito es identificar todos los pedidos cursados por nuestro cliente, devolviendo el UUID único de cada composición basada en Online_Customer_Order_v0.

Partimos de nuestro esqueleto básico de contención:

SELECT ... FROM EHR e CONTAINS COMPOSITION c ...

En el Modelo de Referencia de openEHR, el identificador versionado de la composición se ubica en el atributo uid. Si seleccionamos c/uid directamente, el CDR nos devuelve el objeto OBJECT_VERSION_ID al completo: 

{
  "_type": "OBJECT_VERSION_ID",
  "value": "3b463d4c-1613-410f-b271-3e81a7743549::local.ehrbase.org::1"
}

Si nuestra aplicación consumidora solo necesita la cadena de texto limpia, podemos apuntar directamente a c/uid/value.

¿Conviene seleccionar el objeto completo o solo el valor? Elegir el objeto completo preserva metadatos relevantes (como tipos de datos e identificadores de terminología). Por contra, apuntar directamente a /value ofrece una respuesta más reducida y agiliza el procesamiento en el cliente. En estos ejemplos seleccionamos directamente los valores primitivos.

Seguidamente, acotamos la consulta a la historia de nuestro cliente específico usando su identificador EHR ID (que reside en ehr_id/value dentro del EHR):

SELECT c/uid/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43'

Por último, para evitar coincidencias con otras composiciones (como valoraciones o registros de seguimiento), filtramos estrictamente por el identificador de la plantilla (que se halla en archetype_details/template_id/value dentro de la composición): 

SELECT c/uid/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE 
    e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43' 
    AND 
    c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

AQL 2 — Consultar el estado de preparación de los pedidos

En este supuesto deseamos conocer el estado de elaboración de nuestros pedidos. Esta información reside en composiciones sustentadas en la plantilla Kitchen_And_Delivery_Tracker_v0.

Para descubrir las rutas AQL exactas de estos elementos, abrimos openEHR Archetype Designer. En el detalle del nodo encontramos la ruta resuelta para el Order ID: 

/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]

Figura 10.2: Inspección de la ruta resuelta para el Order ID en Archetype Designer.

De forma idéntica, localizamos la ruta para el estado de transición ISM de la acción (el estado de elaboración): 

/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition

Figura 10.3: Localización de la ruta para el estado de transición ISM.

Componemos la sentencia AQL al completo:

SELECT 
  c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]/value/id, 
  c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition/current_state/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE 
    e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43' 
    AND
    c/archetype_details/template_id/value = 'Kitchen_And_Delivery_Tracker_v0'

Fijar valores constantes en cadenas AQL extensas puede resultar propenso a errores. Sustituyendo los valores literales por parámetros (como $ehr_id y $template_id), obtenemos una consulta limpia, dinámica y reutilizable: 

{
  "q": "SELECT c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]/value/id, c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition/current_state/value FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value=$ehr_id AND c/archetype_details/template_id/value=$template_id",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {
    "ehr_id": "7fab0168-e79f-456f-b271-02050dabaa43",
    "template_id": "Kitchen_And_Delivery_Tracker_v0"
  }
}

Al procesar esta petición, obtenemos el Order ID junto a su estado de elaboración actual:

AQL 3 — Evaluar valoraciones según el nombre de la pizza

Finalmente, determinaremos qué pizza ha recibido la puntuación de satisfacción de cliente más alta.

Aquí encaramos un escenario habitual en el modelado de openEHR: el nombre de la pizza se recogió en el momento de la comanda en Online_Customer_Order_v0, mientras que la puntuación de satisfacción se remitió con posterioridad en Customer_Review_v0. Aunque técnicas avanzadas de AQL posibilitan el enlace de registros relacionados, en entornos reales suele ser más claro, eficiente y robusto ejecutar dos consultas acotadas y cruzarlas mediante su clave común (el Order ID):

  1. Consulta 1: Obtener el nombre de la pizza para cada Order ID.
  2. Consulta 2: Obtener la valoración del cliente para cada Order ID.

Consulta 1: Obtener nombres de pizza por Order ID

{
  "q": "SELECT c/uid/value AS order_id, c/content[openEHR-EHR-INSTRUCTION.pizza_order.v0]/activities[at0001]/description[at0002]/items[at0004]/value/value AS pizza_name FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value=$ehr_id AND c/archetype_details/template_id/value=$template_id",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {
    "ehr_id": "7fab0168-e79f-456f-b271-02050dabaa43",
    "template_id": "Online_Customer_Order_v0"
  }
}
