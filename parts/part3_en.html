Storing and Querying Data in the CDR

In the previous part, we designed a set of archetypes and assembled them into templates to represent a workflow. In this part, we will walk through the core operations required to persist (store) and retrieve clinical data using an openEHR Clinical Data Repository (CDR). We will focus on practical, hands-on steps using standard REST APIs.

Note: Even though we are not using clinical data in the following examples (we keep the pizza delivery analogy) everything shown here is transferable to a clincal workflow.

The Clinical Data Repository (CDR)

As discussed earlier, the CDR is the database that stores and manages healthcare data. Because all compositions stored in an openEHR CDR are strictly governed by templates, the CDR must store the relevant templates before it can accept any compositions based on them.

In this guide, we will use a CDR powered by EHRbase, an open-source openEHR implementation developed by vitagroup AG (vitagroup.ag). While there are several CDR implementations available on the market, EHRbase provides a freely accessible public sandbox that is ideal for learning and testing:

  • Sandbox URL: https://sandkiste.ehrbase.org
  • Full API Documentation: EHRbase openEHR REST API Docs
Security Note: The sandbox is a shared, public environment. Never submit real patient data, passwords, or personal identifying information.

API Testing Tools

To send data to and retrieve data from EHRbase endpoints, we need an HTTP/REST client. Popular tools include Insomnia, Bruno, and Postman. In this tutorial, we will use Postman, though the exact same requests and concepts apply to any API testing tool.

A Short Tour Around Postman

When you first open Postman, do not let the extensive interface intimidate you. For our openEHR workflow, you only need to interact with three primary zones:

  1. Left Sidebar (Your Library): Where your saved requests live. The most important section is Collections, where you organize related requests into folders. Create collections by clicking on the "+" and select "Collection". To create a request in your collection, hover over the collection and click on the "+" that appears beside it.
  2. Top / Middle Panel (The Request Builder): Where you construct your HTTP call:
    • HTTP Method: The verb dropdown (GET, POST, PUT, etc.).
    • URL Bar: The target address of your CDR server.
    • Headers: Metadata describing the payload (e.g., Content-Type: application/json or Prefer: return=representation).
    • Params: URL query parameters or path variables (e.g., :ehr_id or :template_id).
    • Body: The data payload (e.g., the JSON composition or the raw XML of an OPT template).
    • Authorization: Where bearer tokens or basic credentials are configured when interacting with secured systems.
  3. Bottom Panel (The Response Viewer): Displays the CDR's response once you click Send:
    • Status Code: Confirms success (200 OK, 201 Created) or reports issues (400 Bad Request, 404 Not Found).
    • Response Body: The returned data (such as a newly generated EHR ID, composition UID, or query result).
    • Time & Size: Performance metrics for the request.

Figure 3.1: The GUI of Postman.

Core HTTP Verbs in openEHR

To tell the CDR what you wan to achieve with your request you have different "verbs" that you can use: GET, POST, PUT, DELETE, PATCH. For all of our hands-on examples, we will exclusively use GET, POST, and PUT. For the full API capabilities of EHRbase please refer to the API documentation.

HTTP Method Meaning Usage in openEHR & EHRbase
GET Read / Retrieve Fetch data without modifying server state (e.g., download a template or retrieve a composition).
POST Create / Execute Submit new data to be created (e.g., register a new EHR record, commit a new composition, or execute an AQL query payload).
PUT Upload / Replace Store or replace a resource at a specific URI (e.g., upload an Operational Template (OPT) to the template definition endpoint, or update an existing composition version).

Building a Composition from Scratch (Step-by-Step)

Now that our templates are uploaded to the CDR, we can persist actual clinical data. In openEHR, clinical data is stored in the form of a COMPOSITION.

While you could ask EHRbase for a synthetic sample, those auto-generated payloads are full of confusing dummy values and optional attributes that obscure what is actually necessary. The best way to truly understand openEHR data is to build a minimal, valid composition from scratch.

In this walkthrough, we will construct a complete composition for our Customer_Review_v0 template.

Please have a look a the specifications of the COMPOSITION class. It is a good idea to follow the creation of the composition file by using the Reference Model. For fast searches, the unofficial openEHR RM Browser is recommended.

Step 1 - The Anatomy of a COMPOSITION

The COMPOSITION is the container for the complete document we want to persist.At the root level, the openEHR Reference Model expects this skeletal structure: 

{
  "_type": "COMPOSITION",
  "name": { ... },
  "archetype_node_id": "openEHR-EHR-COMPOSITION.example_base.v0",
  "archetype_details": { ... },
  "language": { ... },
  "territory": { ... },
  "category": { ... },
  "composer": { ... },
  "content": [ ... ]
}
Note: This structure is incomplete. We have minimized the elements to keep the examples easy to work with. Please refer to the openEHR specification for a complete list of attributes for a composition.

Now, let us examine and construct each of these attributes one by one.

Step 2 - The name Attribute (RM Class: DV_TEXT)

In openEHR, even simple labels are rarely plain strings. They are wrapped in a Reference Model data type, usually DV_TEXT (Data Value: Text), which allows for localization and character sets.

For the root composition, this usually matches the template name:

"name": {
  "_type": "DV_TEXT",
  "value": "Customer_Review_v0"
}
Note: Depending on how your template was authored, the display name can differ from the underlying archetype identifier.

Step 3 - The archetype_details Attribute (RM Class: ARCHETYPED)

How does the CDR know which rules and constraints to validate this composition against? Through archetype_details. This object connects the composition to both its base root archetype and the specific operational template:

Figure 3.8: Looking at the attribute tree of archetype_details in the openEHR RM Browser.

Notice that archetype_id and template_id are not plain text either; they are instances of the ARCHETYPE_ID and TEMPLATE_ID classes: 

"archetype_details": {
  "_type": "ARCHETYPED",
  "archetype_id": {
    "_type": "ARCHETYPE_ID",
    "value": "openEHR-EHR-COMPOSITION.example_base.v0"
  },
  "template_id": {
    "_type": "TEMPLATE_ID",
    "value": "Customer_Review_v0"
  },
  "rm_version": "1.1.0"
}

Step 4 - Language and Territory (RM Class: CODE_PHRASE)

Healthcare data is multinational. Every composition explicitly defines its primary language and jurisdiction using CODE_PHRASE, which pairs a standard terminology identifier with a specific code.

The supported codes can be found in the openEHR Support Terminology specifications.

Language: ISO 639-1

Figure 3.9: Attribute tree of language.

"language": {
  "_type": "CODE_PHRASE",
  "terminology_id": {
    "_type": "TERMINOLOGY_ID",
    "value": "ISO_639-1"
  },
  "code_string": "en"
}

Territory: ISO 3166-1

Figure 3.10: Attribute tree of territory.

"territory": {
  "_type": "CODE_PHRASE",
  "terminology_id": {
    "_type": "TERMINOLOGY_ID",
    "value": "ISO_3166-1"
  },
  "code_string": "ES"
}

Step 5 - The category Attribute (RM Class: DV_CODED_TEXT)

openEHR categorizes clinical encounters into broad archetypal patterns (such as event, persistent, or episodic). We use DV_CODED_TEXT, which binds human-readable text to an openEHR internal terminology code (here, code 433 represents an point-in-time "event"):

The supported codes can be found in the openEHR Support Terminology specifications.

Figure 3.11: Attribute tree of category.

"category": {
  "_type": "DV_CODED_TEXT",
  "value": "event",
  "defining_code": {
    "_type": "CODE_PHRASE",
    "terminology_id": {
      "_type": "TERMINOLOGY_ID",
      "value": "openehr"
    },
    "code_string": "433"
  }
}

Step 6 - The composer Attribute

Every medical record must track authorship. In openEHR, the composer is modeled as a PARTY_PROXY. You generally choose between:

  • PARTY_SELF: Used when the patient themselves recorded the data (e.g., patient-reported outcome measures / PROMs, mobile apps).
  • PARTY_IDENTIFIED: Used when recording an external person's name or healthcare provider identifier.

Figure 3.12: PARTY_IDENTIFIED chosen to represent the composer.

"composer": {
  "_type": "PARTY_IDENTIFIED",
  "name": "Max Mustermann"
}

Step 7 - The content Section: Adding Clinical Entries

Now we reach the actual payload: the content array. In our template, we placed an EVALUATION archetype (openEHR-EHR-EVALUATION.customer_review.v0).

Figure 3.13: Inspecting the mandatory ENTRY attributes inside content.

Because every entry archetype can theoretically be excerpted, quoted, or translated independently, openEHR requires each entry to define its own localized context:

  • encoding: Character encoding (e.g., UTF-8).
  • language: Language code for this specific entry.
  • subject: Who this clinical evaluation is about. In our case, PARTY_SELF indicates it applies directly to the owner of this record.
  • protocol: Contextual metadata about how or why the entry was recorded (e.g., the Order ID).
  • data: The core clinical observations or evaluations.

Committing a Composition to the CDR

To persist a composition, send an HTTP POST request targeted to the specific patient's ehr_id endpoint:

MethodPOST
URLhttps://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/ehr/:ehr_id/composition
HeadersPrefer: return=representation
Content-Type: application/json
Paramsehr_id = 7fab0168-e79f-456f-b271-02050dabaa43
BodyThe complete Canonical JSON composition.
Expected Status201 Created
Response BodyThe committed composition including its assigned versioned uid.
Understanding the Composition UID: In openEHR, compositions receive an OBJECT_VERSION_ID formatted as {UUID}::{system_id}::{version} (for example: c9214ddc-97eb-4c19-821a-e0aee11d3043::local.ehrbase.org::1).

Modifying an Existing Composition

openEHR repositories maintain a permanent, auditable version history: compositions are never overwritten in-place. When updating a record, we issue an HTTP PUT request and pass the current version ID in the If-Match header to prevent concurrent update conflicts (optimistic locking):

MethodPUT
URLhttps://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/ehr/:ehr_id/composition/:composition_id
HeadersIf-Match: c9214ddc-97eb-4c19-821a-e0aee11d3043::local.ehrbase.org::1
Prefer: return=representation
Content-Type: application/json
Paramsehr_id = 7fab0168-e79f-456f-b271-02050dabaa43
composition_id = c9214ddc-97eb-4c19-821a-e0aee11d3043
BodyThe updated composition JSON.
Expected Status200 OK
Response BodyThe updated record, showing version incremented to ::2.

Figure 3.16: Updating a composition and observing the version increment to ::2.

AQL - Querying Specific Clinical Data

In previous steps, we persisted data into the CDR and saw how to retrieve an entire composition via API when we already know its unique identifier. However, in real clinical applications, you will rarely know the composition ID beforehand, or you will only need specific data points (e.g., only the pizza name, or only the blood pressure systolic reading) across many encounters. For this, openEHR provides the Archetype Query Language (AQL).

AQL is standardized in the official openEHR specifications: openEHR AQL Specifications.

In this section, we will walk through practical examples to give you an intuitive, hands-on first contact with AQL.

Executing an AQL Query via REST API

AQL queries are submitted to EHRbase using an HTTP POST request to the query endpoint:

Method POST
URL https://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/query/aql
Headers Content-Type: application/json
Body Payload - The AQL query envelope in JSON format.
Expected Status 200 OK
Response Body Query result columns and rows in JSON format.

The JSON payload sent in the request body follows this structure:

{
  "q": "SELECT ...",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {}
}
  • q: The AQL query string (mandatory).
  • offset: Number of initial rows to skip (useful for pagination).
  • fetch: Maximum number of rows to return (can also be specified inside the query using LIMIT).
  • query_parameters: A dictionary of key-value parameters substituted into variables declared in the query (prefixed with $).

Standard AQL query strings in JSON must be formatted as a single line. To inspect, format, and document multi-line queries, you can use the open-source openEHR AQL Manager.

The Anatomy of an AQL Query

In broad strokes, an AQL query asks the CDR: "Please return a set of clinical data items based on specific archetype paths and criteria."

For example, comparing a plain English question to its equivalent AQL statement (applied to our pizza delivery analogy):

Motivation: Which customers have placed an order?
Plain Language Question AQL Clause
"Please tell me all EHR IDs..." SELECT e/ehr_id/value
"...of records that contain compositions..." FROM EHR e CONTAINS COMPOSITION c
"...based on the template 'Online_Customer_Order_v0'." WHERE c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

Putting it all together into a complete query:

SELECT e/ehr_id/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

AQL 1 - Listing All Orders for a Customer

Our goal is to find all orders placed by our customer, returning the unique UUID of each composition based on Online_Customer_Order_v0.

We begin with our baseline containment skeleton:

SELECT ... FROM EHR e CONTAINS COMPOSITION c ...

In the openEHR Reference Model, the composition's versioned identifier is located at the uid attribute. If we select c/uid directly, the CDR returns the entire OBJECT_VERSION_ID object: 

{
  "_type": "OBJECT_VERSION_ID",
  "value": "3b463d4c-1613-410f-b271-3e81a7743549::local.ehrbase.org::1"
}

If our client application only needs the string itself, we can point directly to c/uid/value.

Should you select the full object or just the value? Selecting the full object preserves metadata (such as data types and terminology identifiers). On the other hand, pointing straight to /value yields a cleaner payload and minimizes client-side data parsing. In these examples, we select primitive values directly.

Next, we restrict the query to our specific customer record using their EHR ID (which can be found in ehr_id/value of the EHR):

SELECT c/uid/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43'

Finally, to avoid matching other compositions (such as reviews or tracker entries), we filter specifically by template ID (found under archetype_details/template_id/value of the composition): 

SELECT c/uid/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE 
    e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43' 
    AND 
    c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

AQL 2 - Checking Order Preparation Status

In this example, we want to look up the preparation status of our orders. This information is stored in compositions based on the Kitchen_And_Delivery_Tracker_v0 template.

To determine the exact AQL paths for these elements, we consult the openEHR Archetype Designer. Under the node details, we find the resolved path for the Order ID: 

/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]

Figure 3.18: Inspecting the resolved path for the Order ID in the Archetype Designer.

Similarly, we locate the path for the action's ISM transition state (the preparation status): 

/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition

Figure 3.19: Locating the path for the ISM transition state.

We assemble the complete AQL statement:

SELECT 
  c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]/value/id, 
  c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition/current_state/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE 
    e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43' 
    AND
    c/archetype_details/template_id/value = 'Kitchen_And_Delivery_Tracker_v0'

Hardcoding parameters directly into long AQL strings can quickly become error-prone. By replacing literal values with parameters (such as $ehr_id and $template_id), we make our query clean, dynamic, and reusable: 

{
  "q": "SELECT c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]/value/id, c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition/current_state/value FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value=$ehr_id AND c/archetype_details/template_id/value=$template_id",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {
    "ehr_id": "7fab0168-e79f-456f-b271-02050dabaa43",
    "template_id": "Kitchen_And_Delivery_Tracker_v0"
  }
}

Executing this request returns the Order ID and current preparation state:

Figure 3.20: Retrieved order IDs paired with their current preparation status.

AQL 3 - Evaluating Ratings by Pizza Name

Finally, let us determine which pizza received the highest customer satisfaction score.

Here we encounter a realistic openEHR modeling challenge: the pizza name was recorded at ordering time in Online_Customer_Order_v0, whereas the satisfaction rating was submitted later in Customer_Review_v0. While advanced AQL techniques can sometimes link related records, in production environments it is often cleaner and more efficient to execute two focused queries and link them by their common identifier (the Order ID):

  1. Query 1: Retrieve the pizza name for each Order ID.
  2. Query 2: Retrieve the customer rating for each Order ID.

Query 1: Fetching Pizza Names by Order ID

{
  "q": "SELECT c/uid/value AS order_id, c/content[openEHR-EHR-INSTRUCTION.pizza_order.v0]/activities[at0001]/description[at0002]/items[at0004]/value/value AS pizza_name FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value=$ehr_id AND c/archetype_details/template_id/value=$template_id",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {
    "ehr_id": "7fab0168-e79f-456f-b271-02050dabaa43",
    "template_id": "Online_Customer_Order_v0"
  }
}

Figure 3.22: Output mapping order identifiers to specific pizza names.

Query 2: Fetching Ratings by Order ID

{
  "q": "SELECT c/content[openEHR-EHR-EVALUATION.customer_review.v0]/protocol[at0001]/items[at0002]/value/id AS order_id, c/content[openEHR-EHR-EVALUATION.customer_review.v0]/data[at0003]/items[at0005]/value/magnitude AS rating FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value=$ehr_id AND c/archetype_details/template_id/value=$template_id",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {
    "ehr_id": "7fab0168-e79f-456f-b271-02050dabaa43",
    "template_id": "Customer_Review_v0"
  }
}

Figure 3.23: Output mapping order identifiers to numeric satisfaction scores.

By joining the results on order_id, we can see that "Archetype Supreme" was the top-rated pizza for this customer, earning a perfect score of 5!
