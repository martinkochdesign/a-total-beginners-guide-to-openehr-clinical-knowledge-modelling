Speichern und Abfragen von Daten im CDR

Im vorangegangenen Teil haben wir ein Set von Archetypen entworfen und sie zu Templates zusammengefügt, um einen vollständigen Arbeitsablauf abzubilden. In diesem Teil durchlaufen wir die zentralen Schritte, die erforderlich sind, um klinische Daten in einem openEHR Clinical Data Repository (CDR) zu persistieren (speichern) und wieder abzurufen. Der Fokus liegt auf praxisnahen, konkreten Schritten unter Verwendung von Standard-REST-APIs.

Hinweis: Auch wenn wir in den folgenden Beispielen keine echten medizinischen Daten verwenden (wir bleiben bei unserer Pizzalieferungs-Analogie), lässt sich alles hier Gezeigte direkt auf einen realen klinischen Behandlungspfad übertragen.

Das Clinical Data Repository (CDR)

Wie bereits beschrieben, ist das CDR die zentrale Datenbank zur Speicherung und Verwaltung von Gesundheitsdaten. Da alle in einem openEHR-CDR abgelegten Kompositionen streng durch Templates gesteuert werden, muss das CDR die entsprechenden Templates kennen und gespeichert haben, bevor es darauf basierende Kompositionen annehmen kann.

In diesem Leitfaden nutzen wir ein CDR auf Basis von EHRbase, einer quelloffenen openEHR-Implementierung der vitagroup AG (vitagroup.ag). Obwohl verschiedene CDR-Implementierungen am Markt existieren, bietet EHRbase eine frei zugängliche, öffentliche Sandbox, die sich ideal zum Lernen und Testen eignet:

  • Sandbox-URL: https://sandkiste.ehrbase.org
  • Vollständige API-Dokumentation: EHRbase openEHR REST-API-Dokumentation
Sicherheitshinweis: Die Sandbox ist eine öffentlich geteilte Testumgebung. Übermitteln Sie niemals echte Patientendaten, Passwörter oder personenbezogene Daten.

Werkzeuge für API-Tests

Um Daten an die EHRbase-Endpunkte zu senden und von dort abzurufen, benötigen wir einen HTTP/REST-Client. Zu den gängigen Tools zählen Insomnia, Bruno und Postman. In dieser Anleitung nutzen wir Postman; die gezeigten Aufrufe und Konzepte lassen sich jedoch 1:1 auf jedes andere API-Testwerkzeug übertragen.

Ein kurzer Rundgang durch Postman

Lassen Sie sich beim ersten Öffnen von Postman nicht von der Funktionsvielfalt überwältigen. Für unseren openEHR-Ablauf benötigen Sie lediglich drei Hauptbereiche:

  1. Linke Seitenleiste (Ihre Bibliothek): Hier liegen Ihre gespeicherten Anfragen. Der wichtigste Bereich ist Collections (Sammlungen), in dem thematisch zusammenhängende Requests in Ordnern organisiert werden. Neue Sammlungen erstellen Sie mit einem Klick auf das „+“ und Auswahl von „Collection“. Um eine Anfrage anzulegen, fahren Sie mit der Maus über die Sammlung und klicken auf das erscheinende „+“.
  2. Oberes / Mittleres Panel (Der Request-Builder): Hier konfigurieren Sie den HTTP-Aufruf:
    • HTTP-Methode: Das Dropdown-Menü für das Verb (GET, POST, PUT etc.).
    • Adresszeile (URL): Die Zieladresse des CDR-Servers.
    • Header: Metadaten, die den Inhalt beschreiben (z. B. Content-Type: application/json oder Prefer: return=representation).
    • Parameter (Params): URL-Query-Parameter oder Pfadvariablen (z. B. :ehr_id oder :template_id).
    • Body: Die Nutzdaten (z. B. das JSON der Komposition oder der XML-Quelltext eines OPT-Templates).
    • Autorisierung (Authorization): Konfiguration von Bearer-Tokens oder Basic-Auth bei abgesicherten Systemen.
  3. Unteres Panel (Der Response-Viewer): Zeigt die Antwort des CDR an, sobald Sie auf Send geklickt haben:
    • Statuscode: Bestätigt den Erfolg (200 OK, 201 Created) oder meldet Fehler (400 Bad Request, 404 Not Found).
    • Response-Body: Die zurückgegebenen Daten (wie eine neu generierte EHR-ID, die UID einer Komposition oder das Abfrageergebnis).
    • Zeit & Größe: Performancemetriken des Requests.

Zentrale HTTP-Verben in openEHR

Um dem CDR mitzuteilen, was mit der Anfrage bezweckt wird, stehen verschiedene HTTP-Verben zur Verfügung: GET, POST, PUT, DELETE, PATCH. Für all unsere Praxisbeispiele beschränken wir uns auf GET, POST und PUT. Den vollen Funktionsumfang entnehmen Sie bitte der EHRbase-Dokumentation.

HTTP-Methode Bedeutung Einsatz in openEHR & EHRbase
GET Lesen / Abrufen Daten abrufen, ohne den Serverstatus zu verändern (z. B. ein Template herunterladen oder eine Komposition laden).
POST Erstellen / Ausführen Neue Daten an den Server übermitteln (z. B. eine neue Akte/EHR registrieren, eine Komposition anlegen oder eine AQL-Abfrage ausführen).
PUT Hochladen / Ersetzen Eine Ressource an einer definierten URI speichern oder überschreiben (z. B. ein Operational Template (OPT) hochladen oder eine bestehende Komposition aktualisieren).

Ein Operational Template (OPT) auf das CDR hochladen

Bevor eine Komposition gespeichert werden kann, muss das zugehörige Template als Operational Template (.opt-Datei) hochgeladen werden. Das CDR parst diese Definition und wendet alle darin modellierten Einschränkungen auf eingehende Kompositionen an.

Die Beispieldateien der Templates finden Sie im herunterladbaren ZIP-Archiv: Beispieldateien herunterladen (.zip)

MethodePOST
URLhttps://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/definition/template/adl1.4
HeaderPrefer: return=representation
Content-Type: application/xml
BodyDer rohe XML-Inhalt Ihrer .opt-Datei.
Erwarteter Status201 Created
Response-BodyDas registrierte OPT-Template im XML-Format.
Wichtig: Falls auf dem Server bereits ein Template mit exakt derselben template_id existiert, weist das CDR den Upload ab, um die Integrität der Versionierung zu schützen.

Eine Beispiel-Komposition generieren

Bei der Entwicklung von Anwendungen ist es oft hilfreich, rasch eine Beispiel-Komposition für ein Template zur Hand zu haben. Sie können das CDR anweisen, ein synthetisches JSON-Muster basierend auf einem registrierten Template zu erzeugen:

MethodeGET
URLhttps://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/definition/template/adl1.4/:template_id/example?format=JSON
Parameter (Params)template_id = Customer_Review_v0 (je nach Template-ID)
Erwarteter Status200 OK
Response-BodySynthetische Beispiel-Komposition im Canonical JSON-Format von openEHR.
Warnung: Vom CDR generierte Beispiel-Payloads dienen ausschließlich der Syntaxprüfung. Sie befüllen Felder mit zufälligen Werten und dürfen niemals als reale klinische Daten persistiert werden.

Eine Komposition von Grund auf erstellen (Schritt für Schritt)

Nachdem unsere Templates im CDR registriert sind, können wir reale klinische Daten speichern. In openEHR geschieht dies in Form einer COMPOSITION.

Man könnte zwar EHRbase um eine synthetische Vorlage bitten, doch diese autogenerierten Payloads sind voller verwirrender Dummy-Werte und optionaler Attribute, die den Blick auf das Wesentliche verstellen. Der beste Weg, openEHR-Daten wirklich zu verstehen, ist der Bau einer minimalen, validen Komposition von Hand.

In dieser Schritt-für-Schritt-Anleitung bauen wir eine vollständige Komposition für unser Template Customer_Review_v0.

Werfen Sie dazu gerne einen Blick in die Spezifikation der Klasse COMPOSITION. Es empfiehlt sich, den Aufbau der Datei anhand des Referenzmodells nachzuvollziehen. Für schnelle Nachschlagezwecke ist der inoffizielle openEHR RM Browser ideal geeignet.

Schritt 1 – Die Anatomie einer COMPOSITION

Die COMPOSITION dient als Hülle für das gesamte zu speichernde Dokument. Auf oberster Ebene erwartet das openEHR-Referenzmodell folgende Grundstruktur: 

{
  "_type": "COMPOSITION",
  "name": { ... },
  "archetype_node_id": "openEHR-EHR-COMPOSITION.example_base.v0",
  "archetype_details": { ... },
  "language": { ... },
  "territory": { ... },
  "category": { ... },
  "composer": { ... },
  "content": [ ... ]
}
Hinweis: Diese Struktur ist bewusst auf das Wesentliche reduziert, um die Beispiele übersichtlich zu halten. Die vollständige Liste aller Attribute einer Komposition finden Sie in der offiziellen openEHR-Spezifikation.

Lassen Sie uns nun jedes dieser Attribute einzeln betrachten und aufbauen.

Schritt 2 – Das name-Attribut (RM-Klasse: DV_TEXT)

In openEHR sind selbst einfache Bezeichnungen selten reine Strings. Sie werden in Datentypen des Referenzmodells gekapselt – meist in DV_TEXT (Data Value: Text), was Lokalisierung und Zeichensatzangaben ermöglicht.

Für die Basis-Komposition entspricht dies üblicherweise dem Namen des Templates:

"name": {
  "_type": "DV_TEXT",
  "value": "Customer_Review_v0"
}
Hinweis: Je nachdem, wie Ihr Template benannt wurde, kann der Anzeigename vom technischen Bezeichner des zugrundeliegenden Archetyps abweichen.

Schritt 3 – Das archetype_details-Attribut (RM-Klasse: ARCHETYPED)

Woher weiß das CDR, gegen welche Regeln und Einschränkungen diese Komposition validiert werden muss? Über archetype_details. Dieses Objekt verknüpft die Komposition sowohl mit ihrem Basis-Archetyp als auch mit dem spezifischen Operational Template:

Abbildung 3.8: Aufbau von archetype_details im openEHR RM Browser.

Beachten Sie, dass auch archetype_id und template_id kein reiner Text sind, sondern Instanzen der Klassen ARCHETYPE_ID und TEMPLATE_ID: 

"archetype_details": {
  "_type": "ARCHETYPED",
  "archetype_id": {
    "_type": "ARCHETYPE_ID",
    "value": "openEHR-EHR-COMPOSITION.example_base.v0"
  },
  "template_id": {
    "_type": "TEMPLATE_ID",
    "value": "Customer_Review_v0"
  },
  "rm_version": "1.1.0"
}

Schritt 4 – Sprache und Territorium (RM-Klasse: CODE_PHRASE)

Medizinische Daten sind international. Jede Komposition definiert ihre Primärsprache und ihren Rechtsraum explizit über eine CODE_PHRASE, die eine Standard-Terminologiekennung mit einem spezifischen Code verbindet.

Die zulässigen Codes finden sich in den Spezifikationen der openEHR Support Terminology.

Sprache: ISO 639-1

Schritt 5 – Das category-Attribut (RM-Klasse: DV_CODED_TEXT)

openEHR unterteilt klinische Begegnungen in übergeordnete Muster (wie event, persistent oder episodic). Wir nutzen hier DV_CODED_TEXT, das lesbaren Text mit einem internen openEHR-Terminologiecode verknüpft (hier steht Code 433 für ein punktuelles Ereignis bzw. „event“):

Schritt 6 – Das composer-Attribut

Jeder medizinische Datensatz muss seine Urheberschaft nachweisen. In openEHR wird der Verfasser (Composer) über PARTY_PROXY modelliert. Üblicherweise wählt man zwischen:

  • PARTY_SELF: Wird genutzt, wenn der Patient die Daten selbst erfasst hat (z. B. bei Patientenfragebögen / PROMs, Apps).
  • PARTY_IDENTIFIED: Dient der Erfassung des Namens oder Identifikators eines behandelnden Arztes oder einer Einrichtung.

Abbildung 3.12: PARTY_IDENTIFIED zur Abbildung des Verfassers.

"composer": {
  "_type": "PARTY_IDENTIFIED",
  "name": "Max Mustermann"
}

Schritt 7 – Der content-Bereich: Hinzufügen klinischer Einträge

Nun erreichen wir die eigentlichen Nutzdaten: das content-Array. In unserem Template haben wir einen EVALUATION-Archetyp eingebunden (openEHR-EHR-EVALUATION.customer_review.v0).

Abbildung 3.13: Die verpflichtenden ENTRY-Attribute innerhalb von content.

Da jeder Entry-Archetyp theoretisch isoliert zitiert, extrahiert oder übersetzt werden kann, verlangt openEHR, dass jeder Eintrag seinen eigenen lokalen Kontext definiert:

  • encoding: Zeichenkodierung (z. B. UTF-8).
  • language: Sprachcode für diesen spezifischen Eintrag.
  • subject: Auf wen sich diese Evaluation bezieht. In unserem Fall zeigt PARTY_SELF an, dass sie direkt für den Inhaber dieser Akte gilt.
  • protocol: Kontextuelle Metadaten darüber, wie oder warum der Eintrag erfasst wurde (z. B. die Order ID).
  • data: Die eigentlichen fachlichen Beobachtungen oder Bewertungen.

Schritt 7.1 – encoding, language und subject des Inhalts

AQL – Gezielte Abfrage klinischer Daten

In den vorangegangenen Schritten haben wir Daten im CDR persistiert und gesehen, wie man ein ganzes Dokument per API lädt, wenn man dessen ID kennt. In der Praxis weiß man diese ID jedoch selten im Voraus oder benötigt gezielt einzelne Werte (z. B. nur den Pizzanamen oder den systolischen Blutdruckwert) quer über viele Einträge hinweg. Hierfür bietet openEHR die Archetype Query Language (AQL).

AQL ist in den offiziellen openEHR-Spezifikationen genormt: openEHR AQL-Spezifikationen.

In diesem Abschnitt behandeln wir praxisnahe Beispiele, die Ihnen einen intuitiven Ersteinstieg in AQL vermitteln.

Ausführen einer AQL-Abfrage über die REST-API

AQL-Abfragen werden per HTTP-POST an den Abfrage-Endpunkt von EHRbase übermittelt:

Methode POST
URL https://sandkiste.ehrbase.org/ehrbase/rest/openehr/v1/query/aql
Header Content-Type: application/json
Body Nutzdaten: Der AQL-Envelope im JSON-Format.
Erwarteter Status 200 OK
Response-Body Spalten und Zeilen des Abfrageergebnisses in JSON.

Der Request-Body folgt dieser Struktur:

{
  "q": "SELECT ...",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {}
}
  • q: Der eigentliche AQL-Query-String (verpflichtend).
  • offset: Anzahl der zu überspringenden Zeilen zu Beginn (wichtig für Paginierung).
  • fetch: Maximale Zeilenanzahl der Rückgabe (kann auch in der Abfrage per LIMIT definiert werden).
  • query_parameters: Ein Dictionary aus Schlüssel-Wert-Paaren, die Variablen in der Abfrage ersetzen (gekennzeichnet durch $).

Standardmäßige AQL-Query-Strings in JSON müssen einzeilig formatiert sein. Um komplexe mehrzeilige Abfragen übersichtlich zu strukturieren, zu testen und zu dokumentieren, können Sie den quelloffenen openEHR AQL Manager nutzen.

Die Anatomie einer AQL-Abfrage

Im Grunde formuliert eine AQL-Abfrage an das CDR: „Gib mir bitte ein bestimmtes Set an Datenpunkten basierend auf spezifischen Archetyp-Pfaden und Kriterien zurück.“

Vergleichen wir eine natürlichsprachliche Frage mit ihrer Entsprechung in AQL (bezogen auf unser Pizzabeispiel):

Fragestellung: Welche Kunden haben eine Bestellung aufgegeben?
Natürlichsprachliche Frage AQL-Klausel
„Nenne mir bitte alle EHR-IDs...“ SELECT e/ehr_id/value
„...aus Akten, die Kompositionen enthalten...“ FROM EHR e CONTAINS COMPOSITION c
„...basierend auf dem Template 'Online_Customer_Order_v0'.“ WHERE c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

Zusammengefügt zu einer vollständigen Abfrage:

SELECT e/ehr_id/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

AQL 1 – Alle Bestellungen eines Kunden auflisten

Unser Ziel ist es, alle Bestellungen unseres Kunden abzurufen und die eindeutige UUID jeder auf Online_Customer_Order_v0 basierenden Komposition zurückzuerhalten.

Wir beginnen mit dem Basisgerüst:

SELECT ... FROM EHR e CONTAINS COMPOSITION c ...

Im openEHR-Referenzmodell liegt der versionierte Bezeichner der Komposition im Attribut uid. Selektieren wir c/uid direkt, liefert das CDR das vollständige OBJECT_VERSION_ID-Objekt: 

{
  "_type": "OBJECT_VERSION_ID",
  "value": "3b463d4c-1613-410f-b271-3e81a7743549::local.ehrbase.org::1"
}

Benötigt unsere Client-Anwendung lediglich den Textwert, können wir direkt auf c/uid/value verweisen.

Vollständiges Objekt oder reiner Wert? Die Selektion des gesamten Objekts erhält wertvolle Metadaten (wie Datentypen und Terminologie-IDs). Der direkte Zugriff auf /value liefert hingegen eine schlankere Payload und spart Parsing-Arbeit auf Clientseite. In diesen Beispielen selektieren wir direkt die einfachen Werte.

Als Nächstes schränken wir die Abfrage über die EHR-ID auf unseren Kunden ein (abrufbar unter ehr_id/value der EHR):

SELECT c/uid/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43'

Um keine anderen Kompositionen (wie Reviews oder Tracker-Einträge) mit einzubeziehen, filtern wir zusätzlich auf die Template-ID (zu finden unter archetype_details/template_id/value der Komposition): 

SELECT c/uid/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE 
    e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43' 
    AND 
    c/archetype_details/template_id/value = 'Online_Customer_Order_v0'

AQL 2 – Zubereitungsstatus der Bestellungen prüfen

In diesem Beispiel wollen wir den aktuellen Bearbeitungsstatus unserer Bestellungen ermitteln. Diese Information liegt in den Kompositionen des Templates Kitchen_And_Delivery_Tracker_v0.

Um die exakten AQL-Pfade für diese Datenelemente zu ermitteln, schauen wir in den openEHR Archetype Designer. In den Knotendetails finden wir den aufgelösten Pfad für die Order ID: 

/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]

Abbildung 3.18: Ermittlung des aufgelösten Pfads für die Order ID im Archetype Designer.

Genauso ermitteln wir den Pfad für den ISM-Status der Aktion (den Zubereitungsstatus): 

/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition

Abbildung 3.19: Lokalisierung des Pfads für den ISM-Übergangsstatus.

Daraus setzen wir die vollständige AQL-Anweisung zusammen:

SELECT 
  c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]/value/id, 
  c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition/current_state/value 
FROM EHR e 
CONTAINS COMPOSITION c 
WHERE 
    e/ehr_id/value = '7fab0168-e79f-456f-b271-02050dabaa43' 
    AND 
    c/archetype_details/template_id/value = 'Kitchen_And_Delivery_Tracker_v0'

Feste Werte direkt in lange AQL-Strings zu schreiben, birgt Fehlerquellen. Indem wir statische Werte durch Parameter (wie $ehr_id und $template_id) ersetzen, wird unsere Abfrage sauber, dynamisch und wiederverwendbar: 

{
  "q": "SELECT c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/protocol[at0006]/items[at0011]/value/id, c/content[openEHR-EHR-ACTION.pizza_preparation.v0]/ism_transition/current_state/value FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value=$ehr_id AND c/archetype_details/template_id/value=$template_id",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {
    "ehr_id": "7fab0168-e79f-456f-b271-02050dabaa43",
    "template_id": "Kitchen_And_Delivery_Tracker_v0"
  }
}

AQL 3 – Bewertungen nach Pizzanamen analysieren

Schließlich möchten wir herausfinden, welche Pizza die beste Zufriedenheitsbewertung von unserem Kunden erhalten hat.

Hier begegnen wir einer typischen Modellierungsaufgabe in openEHR: Der Name der Pizza wurde zum Bestellzeitpunkt in Online_Customer_Order_v0 hinterlegt, die Bewertung hingegen später in Customer_Review_v0 abgegeben. Während fortgeschrittene AQL-Techniken verknüpfte Suchen erlauben, ist es in Produktivumgebungen oft performanter und robuster, zwei fokussierte Abfragen auszuführen und diese über den gemeinsamen Bezeichner (die Order ID) zu verknüpfen:

  1. Abfrage 1: Abrufen des Pizzanamens zu jeder Order ID.
  2. Abfrage 2: Abrufen der Kundenbewertung zu jeder Order ID.

Abfrage 1: Pizzanamen über die Order ID abrufen

{
  "q": "SELECT c/uid/value AS order_id, c/content[openEHR-EHR-INSTRUCTION.pizza_order.v0]/activities[at0001]/description[at0002]/items[at0004]/value/value AS pizza_name FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value=$ehr_id AND c/archetype_details/template_id/value=$template_id",
  "offset": 0,
  "fetch": 100,
  "query_parameters": {
    "ehr_id": "7fab0168-e79f-456f-b271-02050dabaa43",
    "template_id": "Online_Customer_Order_v0"
  }
}
