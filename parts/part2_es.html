Capítulo 4: Diseñando el flujo de trabajo con arquetipos y plantillas

Antes de abrir cualquier herramienta de software, un modelado clínico eficaz parte siempre de un plano bien trazado. En este capítulo estructuramos un proceso completo de principio a fin utilizando una analogía cercana del sector de la restauración: pedir, preparar y valorar una pizza. Desglosamos el flujo de trabajo en momentos documentales clínicos bien definidos, identificamos las clases de arquetipos necesarias y planificamos las tres plantillas que darán soporte a cada etapa del recorrido.

4.1 La analogía del pedido de pizza

Como hemos aprendido, openEHR modela los datos clínicos en dos capas claramente diferenciadas: conceptos clínicos (arquetipos) y contexto clínico (plantillas).

Para empezar a modelar en la práctica, recurriremos a una analogía con un flujo de trabajo clínico que engloba las distintas clases de arquetipos.

Mantendremos las analogías relacionadas con la comida y modelaremos el proceso de un pedido y entrega de pizza.

Usamos la analogía de la pizza para concentrarnos en la mecánica del modelado sin distraernos con debates clínicos reales.

Para ello, modelaremos el siguiente flujo de trabajo:

  • El cliente envía un pedido a la pizzería a través de un formulario web. Se genera un identificador de pedido (Order ID) para vincular toda la documentación posterior con este pedido concreto.
  • La cocina elabora la pizza y registra su seguimiento hasta la entrega. Cada paso de este seguimiento queda documentado.
  • Tras recibir y disfrutar la pizza, el cliente cumplimenta un formulario de satisfacción.

4.2 Las tres plantillas

Estructuración del proceso

Las plantillas y arquetipos que desarrollaremos para este flujo de trabajo son:

  • Plantilla 1: "Online Customer Checkout"
  • Plantilla 2: "Kitchen and Courier Tracker"
  • Plantilla 3: "Customer Review"

En los siguientes párrafos detallaremos qué plantillas deben contener qué arquetipos y qué elementos de datos debemos modelar en dichos arquetipos.

Arquetipo base

Para mantener las cosas simples, basaremos todas nuestras plantillas en un único arquetipo: openEHR-EHR-COMPOSITION.example_base.v0. En la práctica real, seleccionarías o crearías un arquetipo de composición específico según el propósito previsto, como modelar un encuentro asistencial (encounter), una lista persistente o un informe.

Esta composición base se crea simplemente generando un nuevo arquetipo COMPOSITION con openEHR-EHR-COMPOSITION.example_base.v0 como ID y guardándolo. No requiere ninguna modificación.

Plantilla 1: Pedido del cliente en línea (Online Customer Order)

  • Arquetipo: ADMIN_ENTRY.delivery_address.v0
    • Elemento de datos: Customer Name — Tipo: DV_TEXT
    • Elemento de datos: Delivery Street and Number — Tipo: DV_TEXT
    • Elemento de datos: Contact Phone — Tipo: DV_TEXT
  • Arquetipo: INSTRUCTION.pizza_order.v0
    • Elemento de datos: Pizza Name — Tipo: DV_CODED_TEXT (Archetype Supreme, Semantic Quattro, Midnight Special)
    • Elemento de datos: Size — Tipo: DV_CODED_TEXT (Small, Medium, Large)
    • Elemento de datos: Special Kitchen Notes — Tipo: DV_TEXT (p. ej., "Bien hecha, por favor")
    • Ranura (slot): Extra Toppings (incluye el arquetipo CLUSTER.pizza_topping.v0 descrito abajo)
  • Arquetipo: CLUSTER.pizza_topping.v0 (insertado en INSTRUCTION.pizza_order.v0)
    • Elemento de datos: Topping Name — Tipo: DV_CODED_TEXT (p. ej., Champiñones, Extra de mozzarella, Jalapeños)
    • Elemento de datos: Amount — Tipo: DV_ORDINAL (1: Regular, 2: Doble, 3: Triple)

Plantilla 2: Seguimiento de cocina y entrega (Kitchen and Delivery Tracker)

  • Arquetipo: ACTION.pizza_preparation.v0
    • Elemento de datos: Order ID — Tipo: DV_IDENTIFIER (UUID del pedido)
    • Elemento de datos: ISM Lifecycle State — Tipo: ISM_TRANSITION (Planificada → Al horno → Enviada → Entregada, o Cancelada)
    • Elemento de datos: Baking Temperature — Tipo: DV_QUANTITY (p. ej., 320 °C)
    • Elemento de datos: Notes — Tipo: DV_TEXT (p. ej., "Entregada al cliente en la puerta principal")
    • Ranura (slot): Toppings Verified (reutiliza CLUSTER.pizza_topping.v0 para comprobar qué ingredientes se hornearon realmente)

Plantilla 3: Valoración del cliente (Customer Review)

  • Arquetipo: EVALUATION.customer_review.v0
    • Elemento de datos: Order ID — Tipo: DV_IDENTIFIER (UUID del pedido)
    • Elemento de datos: Satisfaction Rating — Tipo: DV_COUNT (restringido entre 1 y 5)
    • Elemento de datos: Recommend to Friend? — Tipo: DV_BOOLEAN (Verdadero / Falso)
    • Elemento de datos: Customer Feedback — Tipo: DV_TEXT (Comentarios en texto libre)

Capítulo 6: ¡Espera, aún hay más! — Restricción de arquetipos en plantillas

Ensamblar una plantilla rara vez consiste en unir piezas sin tocarlas; la realidad asistencial requiere un ajuste a medida. En este capítulo exploramos el concepto de tomar arquetipos maximales y acotarlos a las necesidades exactas del caso de uso. Analizamos cómo renombrar etiquetas, clonar elementos, restringir listas de valores y ajustar multiplicidades, prestando atención a las precauciones semánticas que todo modelador debe mantener.

Como hemos visto en nuestro ejemplo, resultó bastante sencillo armar una plantilla a partir de arquetipos existentes. Parece simplemente cuestión de usar bloques de construcción reutilizables para crear una estructura. Esta es una analogía que encontramos con frecuencia al hablar de openEHR.

En la práctica, esto no refleja toda la realidad. Los arquetipos se diseñan con una gran cantidad de elementos y opciones que no se necesitan o que deben modificarse en la plantilla. Esto significa que no solo ensamblamos piezas, sino que las modificamos durante el montaje. Por eso, en mi empeño por vincularlo todo con la comida, introduje la idea de "hornear" la plantilla, donde los "ingredientes" (arquetipos) se transforman en el proceso.

Esta modificación puede adoptar diferentes formas, entre las que se incluyen:

  • Cambiar el nombre de elementos
  • Clonar elementos
  • Clonar arquetipos
  • Restringir opciones
  • Limitar el número de instancias

Ten presente que cualquier modificación conlleva el riesgo de alterar el significado del elemento de datos o del arquetipo, y podría ocasionar dificultades técnicas más adelante.

6.1 Cambiar el nombre de elementos

Puedes cambiar fácilmente el nombre de un elemento de datos o de un arquetipo. Ten la precaución de no asignar un nombre que contradiga el propósito original para el que fue diseñado dicho elemento.

Figura 6.1: Modificación de nombres de elementos y arquetipos en la plantilla.

6.2 Clonar elementos

Si la "ocurrencia" de un elemento de datos permite la existencia de múltiples instancias, dicho elemento de datos puede clonarse.

Figura 6.2: Clonación de elementos de datos con ocurrencia múltiple.

6.3 Clonar arquetipos

Si la "ocurrencia" de un arquetipo permite la existencia de múltiples instancias, dicho arquetipo puede clonarse.

Figura 6.3: Clonación de arquetipos completos en el árbol de la plantilla.

6.4 Restringir opciones

Cuando el arquetipo proporciona una lista de códigos internos, en la plantilla podemos "desmarcar" opciones. Esto es siempre restrictivo: en la plantilla nunca podemos añadir una opción nueva a una lista de selección.

Figura 6.4: Restricción de códigos internos desmarcando opciones.

6.5 Limitar el número de instancias

Si una ocurrencia de un arquetipo o elemento de datos es "abierta", admitiendo múltiples instancias, podemos limitarla.

Figura 6.5: Restricción del número de ocurrencias en la plantilla.

Esta restricción de ocurrencias solo puede ser "restrictiva", yendo de más a menos. No puedes "abrir" ocurrencias cambiando, por ejemplo, de 0..1 (opcional, pero con un máximo de 1 ocurrencia) a 0..* (opcional, permitiendo infinitas ocurrencias).
