Modelar un proceso con arquetipos y plantillas

Como hemos aprendido, openEHR modela los datos clínicos en dos capas claramente diferenciadas: conceptos clínicos (arquetipos) y contexto clínico (plantillas).

Para empezar a modelar en la práctica, utilizaremos una analogía con un flujo de trabajo clínico que abarca las distintas clases de arquetipos.

Siguiendo con las analogías gastronómicas, modelaremos el proceso de pedido y entrega de una pizza.

Utilizamos la analogía de la pizza para centrarnos en la mecánica del modelado sin distraernos con debates clínicos reales.

Para ello, modelaremos el siguiente flujo de trabajo:

  • El cliente envía un pedido a la pizzería a través de un formulario online. Se genera un Order ID (identificador de pedido) para vincular toda la documentación posterior con este pedido concreto.
  • La cocina prepara la pizza y realiza el seguimiento hasta su entrega. Cada paso de este seguimiento queda documentado.
  • Tras recibir y disfrutar de la pizza, el cliente completa un formulario de satisfacción.

Figura 2.1: El proceso de entrega de la pizza y las tres documentaciones que se derivan de él.

Estructurar el proceso

Las plantillas y arquetipos que desarrollaremos para este flujo de trabajo son:

  • Plantilla 1: "Pedido online del cliente" (Online Customer Checkout)
  • Plantilla 2: "Seguimiento de cocina y repartidor" (Kitchen and Courier Tracker)
  • Plantilla 3: "Reseña del cliente" (Customer Review)

En los siguientes apartados definiremos qué plantillas deben contener qué arquetipos y qué elementos de datos modelaremos dentro de cada arquetipo.

Arquetipo base

Para mantener las cosas simples, basaremos todas nuestras plantillas en un único arquetipo: openEHR-EHR-COMPOSITION.example_base.v0. En la práctica clínica real, seleccionarías o crearías un arquetipo de composición específico según el propósito previsto, como modelar un contacto asistencial (encounter), una lista persistente o un informe.

Esta composición base se construye creando un nuevo arquetipo de tipo COMPOSITION con el ID openEHR-EHR-COMPOSITION.example_base.v0 y guardándolo. No requiere ninguna modificación adicional.

Plantilla 1: Pedido online del cliente

  • Arquetipo: ADMIN_ENTRY.delivery_address.v0
    • Elemento de datos: Nombre del cliente — Tipo: DV_TEXT
    • Elemento de datos: Calle y número de entrega — Tipo: DV_TEXT
    • Elemento de datos: Teléfono de contacto — Tipo: DV_TEXT
  • Arquetipo: INSTRUCTION.pizza_order.v0
    • Elemento de datos: Nombre de la pizza — Tipo: DV_CODED_TEXT (Archetype Supreme, Semantic Quattro, Midnight Special)
    • Elemento de datos: Tamaño — Tipo: DV_CODED_TEXT (Small, Medium, Large)
    • Elemento de datos: Notas especiales para la cocina — Tipo: DV_TEXT (p. ej., "Muy hecha, por favor")
    • Ranura (slot): Ingredientes adicionales (incluye CLUSTER.pizza_topping.v0 a continuación)
  • Arquetipo: CLUSTER.pizza_topping.v0 (insertado en INSTRUCTION.pizza_order.v0)
    • Elemento de datos: Nombre del ingrediente — Tipo: DV_CODED_TEXT (p. ej., Champiñones, Extra de mozzarella, Jalapeños)
    • Elemento de datos: Cantidad — Tipo: DV_ORDINAL (1: Regular, 2: Doble, 3: Triple)

Plantilla 2: Seguimiento de cocina y repartidor

  • Arquetipo: ACTION.pizza_preparation.v0
    • Elemento de datos: Order ID — Tipo: DV_IDENTIFIER (UUID del pedido)
    • Elemento de datos: Estado del ciclo de vida ISM — Tipo: ISM_TRANSITION (Planificado → En el horno → Enviado → Entregado, o Cancelado)
    • Elemento de datos: Temperatura de horneado — Tipo: DV_QUANTITY (p. ej., 320 °C)
    • Elemento de datos: Notas — Tipo: DV_TEXT (p. ej., "Entregado al cliente en la puerta principal")
    • Ranura (slot): Ingredientes verificados (reutiliza CLUSTER.pizza_topping.v0 para contrastar qué se horneó realmente)

Plantilla 3: Reseña del cliente

  • Arquetipo: EVALUATION.customer_review.v0
    • Elemento de datos: Order ID — Tipo: DV_IDENTIFIER (UUID del pedido)
    • Elemento de datos: Puntuación de satisfacción — Tipo: DV_COUNT (restringido entre 1 y 5)
    • Elemento de datos: ¿Recomendarías a un amigo? — Tipo: DV_BOOLEAN (Verdadero / Falso)
    • Elemento de datos: Comentarios del cliente — Tipo: DV_TEXT (Comentarios en texto libre)

¡Un momento, aún hay más! Restringir arquetipos en las plantillas

Como hemos visto en nuestro ejemplo, ha sido relativamente sencillo ensamblar una plantilla a partir de arquetipos existentes. Se asemeja a unir bloques de construcción reutilizables para levantar una estructura. Esta es una analogía muy habitual cuando se habla de openEHR.

En la práctica, esto no es toda la verdad. Los arquetipos se crean con una gran cantidad de elementos y opciones que no se necesitan o que deben modificarse en la plantilla. Esto significa que no nos limitamos a ensamblar bloques de construcción: los modificamos durante el ensamblaje. Por eso, en mi empeño por vincularlo todo a la comida, introduje la idea de «hornear» la plantilla, donde los «ingredientes» (arquetipos) se transforman en el proceso.

Esta modificación puede adoptar diferentes formas, entre ellas:

  • Cambiar el nombre de los elementos
  • Clonar elementos
  • Clonar arquetipos
  • Restringir opciones
  • Limitar el número de instancias

Ten muy presente que cualquier modificación conlleva el riesgo de alterar el significado clínico del elemento de datos o del arquetipo, y puede generar dificultades técnicas más adelante.

Cambiar el nombre de los elementos

Puedes cambiar fácilmente el nombre de un elemento de datos o de un arquetipo. Ten cuidado de no modificar el nombre hacia algo que contradiga el uso clínico previsto de dicho elemento.

Figura 2.24: Modificación del nombre de un nodo en la plantilla.

Clonar elementos

Si la «ocurrencia» de un elemento de datos permite la existencia de múltiples instancias, este elemento de datos se puede clonar.

Figura 2.25: Clonación de un elemento de datos en la plantilla.

Clonar arquetipos

Si la «ocurrencia» de un arquetipo permite la existencia de múltiples instancias, este arquetipo se puede clonar.

Figura 2.26: Clonación de un arquetipo completo.

Restringir opciones

Cuando el arquetipo proporciona una lista de códigos internos, en la plantilla podemos «desmarcar» opciones. Esto siempre es restrictivo: nunca podemos añadir una opción a una selección codificada desde la plantilla.

Figura 2.27: Restricción de opciones en la lista de selección.

Limitar el número de instancias

Si la ocurrencia de un arquetipo o elemento de datos es «abierta», permitiendo múltiples instancias, podemos limitarla.

Figura 2.28: Restricción del número de ocurrencias en la plantilla.

Esta restricción de las ocurrencias solo puede ser «restrictiva», yendo de más a menos. No es posible «abrir» las ocurrencias cambiando, por ejemplo, de 0..1 (opcional, pero como máximo 1 ocurrencia) a 0..* (opcional, con infinitas ocurrencias permitidas).
