Next Steps

Congratulations!

If you have followed along from Part 1 through Part 3, you have accomplished what many find intimidating: you created clinical archetypes, combined them into an Operational Template (OPT), uploaded them to an open-source CDR (EHRbase), persisted clinical (well... pizza-related) compositions using REST APIs, and queried specific data points using AQL.

What's next?

Moving from our small sandbox tutorial to a production-grade healthcare system introduces new challenges. So, what are the next things to have a look at?

Browse Existing Templates and Learn Common Archetype Inclusion Patterns

You do not have to reinvent the wheel when building new templates. Real-world templates frequently reuse classic structural patterns, such as plugging a device or anatomical location cluster into an observation, or embedding adverse reaction risk inside an admission summary. Exploring published templates and analyzing Archetype Inclusion Patterns helps you understand how experienced modellers arrange clusters inside slots and organize clinical sections.

Play with Multiplicity: Existence vs. Occurrences vs. Cardinality

In openEHR, all three constraints are written in the same interval format (such as [0..1], [1..1], or [1..*]), which often causes confusion. However, they control completely different levels of the model:

  • Existence (Object Attributes): Defines whether an attribute of a Reference Model class is mandatory or optional when building a composition. It can only ever be [0..1] (optional) or [1..1] (mandatory). This is defined by the Reference Model itself rather than the modeller — for instance, in a DV_QUANTITY, magnitude and units are mandatory ([1..1]), while precision is optional ([0..1]).
  • Occurrences (Node Instances): Defines how many copies of a specific modeled data element or slot can appear (e.g., 0..1, 1..1, 0..*). This is what you configure most often as a modeller in archetypes and templates (e.g., allowing only 1 primary diagnosis vs. multiple secondary symptoms).
  • Cardinality (List Containers): Defines the total number of items allowed inside a container list attribute (such as items, events, or participations). It is usually left at its standard openEHR default ([0..*] or [1..*]). If a committed composition has fewer or more items than allowed in that list, the CDR rejects it with an Unprocessable Entity (Attribute does not match cardinality) error.

Beyond Ad-Hoc Queries: Stored AQLs

In Part 3, we sent our AQL statements directly inside the HTTP body of a POST /query/aql request. While ad-hoc queries are great for exploration and testing, sending raw query strings from clinical frontends (like hospital EHR screens or patient portals) in production is a big no-no.

Instead, production CDRs use Stored AQLs: version-controlled query definitions registered on the server under a qualified name (e.g., org.openehr::pizza_orders/1.0.0). Frontends simply call this endpoint with parameters like $ehr_id, keeping internal archetype paths secure, execution plans optimized, and clinical logic centralized.

Advanced AQL Concepts to Explore Next

Once you are comfortable with basic SELECT ... FROM ... WHERE statements, you will want to explore more expressive AQL features, such as:

  • Aggregation functions
  • Add variable names to the selected items, using AS
  • Ordering & pagination with LIMIT, OFFSET and ORDER BY
  • Terminology filtering with matches
  • Correlated queries. Linking related compositions using business identifiers across separate entries.

Use of the International CKM

The Clinical Knowledge Manager (CKM) is the global collaborative library where international clinical experts review and standardize archetypes. The golden rule of openEHR modeling is: always search the CKM before creating an archetype.

Explore and get used to the features of the international CKM.

Understand the Boundaries and Limitations of openEHR

openEHR is an exceptional technology for clinical data persistence, but it is not everything you need for a clinical workflow. It is a good idea to eplore how to integrate the use of openEHR into the following:

  • Workflow & Business Process Engines: openEHR documents the clinical state of an action (via ISM transitions), but it is not a BPMN process motor directing hospital tasks.
  • Access Control & User Authorization: Role-based access (RBAC) and user authentication (OAuth2 / OpenID Connect) sit in your application gateway or identity provider, not in the archetype.
  • UI Rendering: Archetypes describe clinical semantics, not whether a field renders as a toggle, radio button, or segmented slider.

Linking to External Terminologies: Term Mapping vs. Term Binding

openEHR archetypes have their own internal code sets (like at0001, at0005), but real systems must connect to global (or local) terminologies like SNOMED CT, LOINC, or ICD-10. YOu might want to explore further into term bindings and term mapping.

As your models mature, you will need to connect them to global clinical standards like SNOMED CT, LOINC, or ICD-10. It is essential to distinguish between three concepts that are often confused: Term Definitions give human-readable names and descriptions to an archetype's internal codes (atnnnn) across multiple languages; Term Bindings link those internal archetype nodes directly to external standards at design time (in the archetype/template); and Term Mappings record external terminology matches directly on clinical values inside a patient's composition at run time.

Translations and Data Element Labels

Archetypes are inherently multi-lingual: the same node identifier (e.g. at0005) can hold language definitions for Catalan, Spanish, English, and German in the archetype itself, for example. Furthermore, it is important to note the distinction between:

  • The template label: The name agreed upon by clinical knowledge modellers during the development of a template.
  • The UI display label: The localized, context-specific alias shown to a specialist on a particular screen (e.g., "BP" on an intensive care dashboard vs. "Blood Pressure Check" on a patient tablet).

As we have learned, the use of multi-lingual templates is problematic. There has to be a governance, that determines from outside of openEHR templates the translations and the UI display labels. There is no standard way to do it, so it needs further exploring anfd figuring out.

Translation Between FHIR and openEHR (via FHIRConnect)

A modern digital health architecture rarely chooses between openEHR and HL7 FHIR, it might use both. openEHR provides the structured, versioned, longitudinal core repository (CDR), while FHIR serves as the exchange standard for APIs and external communications. Sometimes it is going to be necessary to convert incoming messages in FHIR to openEHR for persistance in the CDR.

Using declarative mapping engines such as FHIRConnect, you can define bidirectional mappings between openEHR templates and FHIR resources (like Observation, Condition, or CarePlan).
