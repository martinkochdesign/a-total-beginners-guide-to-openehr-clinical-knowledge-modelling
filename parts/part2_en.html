Modelling a process with archetypes and templates

As we have learned, openEHR models clinical data across two clear layers: clinical concepts (archetypes) and clinical context (templates).

To start modeling in practice, we are going to use an analogy to a clinical workflow that encompasses the different archetype classes.

We are going to keep with the food related analogies and we are going to model the process of a pizza order and delivery.

We use the pizza analogy so we can focus on the modeling mechanics without getting distracted by real clinical debates.

For this, we are going to model the following workflow:

  • The customer sends an order to the pizzeria via an online form. An Order ID is created to link subsequent documentation back to this specific order.
  • The kitchen prepares and tracks the pizza until delivery. Every step of this tracking is documented.
  • After receiving and enjoying the pizza, the customer fills out a customer satisfaction form.

Figure 2.1: The pizza delivery process and the three documentations that emerge from it.

Structuring the process

The templates and archetypes we will develop for this workflow are:

  • Template 1: "Online Customer Checkout"
  • Template 2: "Kitchen and Courier Tracker"
  • Template 3: "Customer Review"

In the following paragraphs we will map out which templates shoud contain which archetypes and which data elements we have to model in the archetypes.

Base archetype

To keep things simple, we will base all our templates on a single archetype: openEHR-EHR-COMPOSITION.example_base.v0. In real-world practice, you would select or create a specific composition archetype depending on its intended purpose. such as modeling an encounter, a persistent list, or a report.

This base composition is made by creating a new COMPOSITION archetype with openEHR-EHR-COMPOSITION.example_base.v0 as the ID and saving it. No modifications needed.

Template 1: Online Customer Order

  • Archetype: ADMIN_ENTRY.delivery_address.v0
    • Data element: Customer Name — Type: DV_TEXT
    • Data element: Delivery Street and Number — Type: DV_TEXT
    • Data element: Contact Phone — Type: DV_TEXT
  • Archetype: INSTRUCTION.pizza_order.v0
    • Data element: Pizza Name — Type: DV_CODED_TEXT (Archetype Supreme, Semantic Quattro, Midnight Special)
    • Data element: Size — Type: DV_CODED_TEXT (Small, Medium, Large)
    • Data element: Special Kitchen Notes — Type: DV_TEXT (e.g., "Well done, please")
    • Slot: Extra Toppings (includes CLUSTER.pizza_topping.v0 below)
  • Archetype: CLUSTER.pizza_topping.v0 (slotted into INSTRUCTION.pizza_order.v0)
    • Data element: Topping Name — Type: DV_CODED_TEXT (e.g., Mushrooms, Extra Mozzarella, Jalapeños)
    • Data element: Amount — Type: DV_ORDINAL (1: Regular, 2: Double, 3: Triple)

Template 2: Kitchen and Delivery Tracker

  • Archetype: ACTION.pizza_preparation.v0
    • Data element: Order ID — Type: DV_IDENTIFIER (UUID of the order)
    • Data element: ISM Lifecycle State — Type: ISM_TRANSITION (Planned → In Oven → Dispatched → Delivered, or Cancelled)
    • Data element: Baking Temperature — Type: DV_QUANTITY (e.g., 320 °C)
    • Data element: Notes — Type: DV_TEXT (e.g., "Handed to customer at front gate")
    • Slot: Toppings Verified (reuses CLUSTER.pizza_topping.v0 to cross-check what was actually baked)

Template 3: Customer Review

  • Archetype: EVALUATION.customer_review.v0
    • Data element: Order ID — Type: DV_IDENTIFIER (UUID of the order)
    • Data element: Satisfaction Rating — Type: DV_COUNT (constrained between 1 and 5)
    • Data element: Recommend to Friend? — Type: DV_BOOLEAN (True / False)
    • Data element: Customer Feedback — Type: DV_TEXT (Free-text comments)

Modelling our 3 templates

Now that all our archetypes are defined, we can assemble them into our 3 templates.

Modelling Template 1: "Online Customer Checkout"

Based on openEHR-EHR-COMPOSITION.example_base.v0, create the template Online_Customer_Order_v0.

Under content, add:

  • openEHR-EHR-ADMIN_ENTRY.delivery_address.v0
  • openEHR-EHR-INSTRUCTION.pizza_order.v0

Select the Extra Toppings CLUSTER slot inside the instruction and slot in openEHR-EHR-CLUSTER.pizza_topping.v0.

That's it! Let's move on to the next template.

Modelling Template 2: "Kitchen and Courier Tracker"

Following the same approach with openEHR-EHR-COMPOSITION.example_base.v0, create the template Kitchen_And_Delivery_Tracker_v0.

Under content, add:

  • openEHR-EHR-ACTION.pizza_preparation.v0

Select the Toppings Verified CLUSTER slot and insert openEHR-EHR-CLUSTER.pizza_topping.v0.

Modelling Template 3: "Customer Review"

Now for our final template: based on openEHR-EHR-COMPOSITION.example_base.v0, create Customer_Review_v0.

Under content, add:

  • openEHR-EHR-EVALUATION.customer_review.v0

Wait, there is more! - Restricting archetypes in templates

As we have seen in our example, it was quite easy to assemble a template from existing archetypes. It just looks like using reusable building blocks to create a structure. This is an analogy that we find often when talking about openEHR.

In practice, this is not the whole truth. Archetypes are created to have a lot of elements and options that are not needed or have to be changed in the template. This means that we are not merely assembling building blocks, we are modifying the blocks during assembly. That's why, on my mission to make everything food related, I introduced the idea of the "baking" of the template, where the "ingredients" (archetypes) are changed in the process.

The modification can take different forms. This includes, but is not limited to:

  • Changing element names
  • Cloning elements
  • Cloning archetypes
  • Restricting options
  • Constraining number of instances

Be aware that any modification bears a risk of changing the significance of the data element or archetype and it might lead into technical difficulties further down the line.

Changing element names

You can easily change the name of a data element or an archetype. Beware that you should not change the name to something that goes against the intended use of this element.

Cloning elements

If the "occurrence"of a data element permits the existence of multiple instances, this data element can be cloned.

Cloning archetypes

If the "occurrence"of an archetype permits the existence of multiple instances, this archetype can be cloned.

Restricting options

When a list of internal codes is provided by the archetype, in the template we can "deselect" options. This is always restrictive. We cannot add an option to a selection in the template.

Constraining number of instances

If an occurrence of an archetype or data element is "open", permitting multiple instances, we can constrain this.

This restriction of occurrences can only be "restrictive", going from more to less. You cannot "open up" occurrences by changing for example 0..1 (optional, but maximum 1 occurrence) to 0..* (option, with infinite occurrences allowed).
